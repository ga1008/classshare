# 问题反馈会话改进

## 现状与范围

原反馈由 `app_feedback` 保存正文，`app_feedback_attachments` 保存截图；提交后仅通知超管，管理页没有回复或状态操作。用户可查看、随时删除反馈。部分接口只按数值用户 ID 授权，在教师与学生 ID 重合时存在越权风险。

本次将每条反馈作为独立会话，提交者与平台超管持续沟通。保留反馈主题、类型、来源页面、原文和截图，并复用消息中心通知。反馈不会混入教学私信的课堂范围，也不建立额外联系人关系。

## 业务规则

- 提交者与所有超管可查看、回复同一条反馈，其他用户无权访问。身份始终使用 `(role, id)`。
- 待处理反馈开始交流后转为处理中，回复不自动关闭。只有超管可以关闭或重新开启。
- 关闭后保留完整历史并停止回复和截图上传；重新开启后继续原会话。
- 关闭、重新开启作为时间线事件保留操作人及说明；客户端提交所见最后消息版本，若已有新消息则先刷新确认。
- 仅尚未交流、仍开放的反馈可以撤回；已交流反馈不再允许硬删除，防止破坏双方记录。
- 回复与状态变动通知对方；超管之间共享历史，各自保留已读进度。通知直达对应反馈。

## 数据与并发

仅新增 `app_feedback_messages` 和 `app_feedback_reads` 及必要索引，不搬迁、覆盖或清空旧表。旧正文继续作为会话起始内容；历史 `pending` 自然可进入新流程，`closed`、`resolved` 保持已结束含义。

会话写入使用数据库事务及 PostgreSQL 行锁串行化回复、关闭、上传和撤回。客户端操作键防止重试产生重复消息/通知；状态操作使用最后消息 ID 检测过期操作。已读游标单调前进且受会话消息范围限制。列表和消息采用有上限的游标分页，不读取无界历史。

## 验收与发布

覆盖提交、双向回复、通知、已读、关闭、关闭后拒绝回复、重新开启、撤回限制、同 ID 不同角色隔离、无关用户拒绝访问、重复请求及关闭竞争。浏览器检查桌面和移动布局、刷新持久化、失败后保留草稿。

发布使用原生 PostgreSQL 新鲜备份进行增量迁移、完整启动与重复初始化预演；确认历史数据及序列不受损。部署前执行 DryRun，正式部署时停写并另取切换备份，保护生产运行目录。上线后核对表结构、原反馈/截图指纹、部署版本和服务健康，再推送远端 Git。

回滚优先恢复上一版代码，新表可保留；原反馈与截图结构兼容旧代码。数据库备份用于异常灾难恢复，不以预演数据库替换生产数据。
