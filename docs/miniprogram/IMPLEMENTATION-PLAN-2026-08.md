## 1. 平台业务链条全景（比对基准）

平台 = FastAPI 单后端，Web 端（Jinja + islands）与小程序共用。按角色梳理业务链条：

### 1.1 学生端业务链

```
登录 → 首页(欢迎语/议程/统计/3D课表) → 课堂
  ├─ 作业考试：列表 → 作答(草稿/附件/倒计时) → 提交 → 互评(小组) → 成绩/批语 → 错题本
  ├─ 课堂现场：签到 → 课堂互动(答题/弹幕) → 投票 → 分组协作(组内对话/目标进度)
  ├─ 学习：学习文档/课后材料 → 材料渲染 → 学习进度 → 个性化学习路径
  ├─ AI：AI 助手聊天(平台知识/学业上下文) → 职业路线星图 → 心理测试/侧写
  ├─ 成长：修为值/成就/连续打卡 → 积分商城 → 成绩单(report card)
  └─ 个人：资料/签名库(上传/审批/使用记录) → 消息中心 → 博客社区
```

对应路由/服务（文件在 `classroom_app/routers/`、`classroom_app/services/`）：

|---|---|---|

| 作业考试 | `homework.py` + `homework_parts/*`（`/api`） | `assignment_lifecycle_service`、`load_student_task_buckets`（三桶单一真源）、`group_assignment_service`、`late_submission_policy` |

### 1.2 教师端业务链

```
教务同步(课程/班级/名册/排课) → 备课(教案/材料库/课次文档)
  → 上课(课堂互动大屏/签到/分组大屏/投票)
  → 批改(提交进度 → 逐份批阅/AI批改 → 迟交策略 → 缺交记零)
  → 归因(错题归集/知识点掌握度)
  → 收尾(结课一键收口 → 成绩材料链: 平时成绩表→登分表→期末成绩单
         → 过程材料: 考核计划表/评学表/教案导出 → 重修生管理)
旁支：监考/考试邮件提醒、课时统计、公文同步、消息中心
```

### 2.2 现存混乱与欠账（这是"推进缓慢且混乱"的根源）

1. **信息架构偏离设计**：DESIGN.md 规划学生/教师各 4 tab（含"课堂"tab），实际只有 3 个纯文字 tab（首页/作业考试/我的），教师与学生混用同一组 tab，教师功能藏在"作业考试"分支里，角色心智不清。tabBar 无图标。
2. **没有差距清单驱动**：P2/P3 标签用完后，后续（互评、预览、批阅改版）全是散点式推进，无里程碑、无版本-功能对照。
3. **移动端最大价值场景缺失**：通知提醒（订阅消息）完全没做——作业截止/批改完成/催交都收不到，用户不打开就没有触达，留存无从谈起。
4. **课堂现场零覆盖**：签到、课堂互动、投票在小程序上全部没有——而"上课时掏手机"恰是小程序相对 Web 最强的场景。
5. **闭环断点**：学生交完作业能看分数，但错题本、成绩单、修为值在小程序上不可见；"我的"页只有退出登录，几乎是空壳。
6. **体验欠账**：深色模式未做、弱网重试策略未系统化、分享转发未接、绘图题仍提示"去网页端"。
7. **运营待办悬置**：测试账号（微信审核/9999001、测试学生/9999002）未删；备案主体名称是否仍为旧名 SentimentRoom 未核对；v0.9.6 提审未点。

## 3. 差距分析与价值排序

不是所有 Web 功能都该搬。按"移动场景适配度 × 用户价值 × 实施成本"排序：

| 优先级 | 功能域 | 移动场景理由 | 成本 |
|---|---|---|---|
| ★★★ | 订阅消息通知（截止/批改完成/催交） | 触达是小程序的独有能力，Web 端做不到；直接决定留存 | 中（需微信模板申请+scheduler 对接） |
| ★★★ | 课堂签到 + 互动答题 + 投票参与 | 上课现场人手一部手机，点击即达，比开网页快一个数量级 | 中 |
| ★★☆ | 成绩/错题/修为（学习闭环只读视图） | 碎片时间查看，纯投影低成本 | 低 |
| ★★☆ | 消息中心聚合 | 配合通知形成"收到推送→进小程序看详情"闭环 | 低 |
| ★★☆ | AI 助手聊天 | 移动端天然对话场景；复用既有 gateway | 中 |
| ★☆☆ | 教师移动工作台（今日课表/监考提醒/一键催交） | 教师在路上/课间的高频快查 | 中 |
| ★☆☆ | 学习材料只读浏览 | 有价值但 HTML 包/复杂文档在小程序渲染受限，只做轻量投影 | 中 |
| ✗ 不做 | 博客、职业星图、签名管理、协作大屏、成绩材料链、教案/过程材料、管理端 | 桌面/大屏场景或低频重操作，留在 Web | — |

## 4. 目标信息架构（定稿后不再漂移）

同一小程序按角色渲染 4 tab（`wx.setTabBarItem` 动态换文案图标，或自绘 tabbar）：

```
学生：今天 · 任务 · 课堂 · 我的
  今天   = 欢迎语 + 大议程卡(含通知未读) + 统计
  任务   = 作业考试三桶(现有 tasks 页)
  课堂   = 签到入口 + 进行中的互动/投票 + 我的课程列表
  我的   = 成绩单 · 错题本 · 修为/积分 · 消息中心 · AI 助手入口 · 设置/退出

教师：今天 · 任务 · 课堂 · 工作台
  今天   = 议程(今日课程/监考/待批) + 统计
  任务   = 作业进度卡列表(现有教师分支) → 批阅
  课堂   = 发起签到 · 发起投票 · 互动最小集 · 我的课堂列表
  工作台 = 本周课表 · 消息中心 · 催交中心 · 设置/退出
```

设计原则沿用：磨砂玻璃令牌、每页一个主任务、大卡片不堆九宫格；tabBar 本期补齐图标（4 组 PNG，选中/未选中）。

## 6. 工程推进机制（防再次失序）

1. **单一真源**：本文件是小程序推进唯一路线图。每完成一项勾选并注版本号/commit；新想法先进"候选池"（§9），不插队。
2. **里程碑纪律**：进行中的里程碑未验收，不开下一个的功能开发（打磨类小项可穿插）。每里程碑收尾动作固定：全量测试绿 → 部署生产 → 上传体验版 → 真机验收清单过一遍 → 用户提审 → 在本文档记录。
3. **API 红线**（重申）：小程序直调既有 `/api/*`；`/api/mp/*` 只做聚合/投影/绝对化 URL 之类的小程序适配；发现要"复制业务逻辑"就停下来改成复用。
4. **版本规范**：`v0.<里程碑序号>.<修订>`；上传描述写"M{n} <内容>"。
5. **测试要求**：每个新 mp 端点有纯函数单测（仿 `tests/test_wechat_mp_teacher_grading.py`）；路由快照重生成；涉及提交/批改/签到等写路径必须真 PG 冒烟后才部署。
6. **用户操作项显式交办**：微信后台操作（提审、发布、订阅消息模板申请、类目材料）无法代办（mp.weixin.qq.com 被浏览器安全策略封锁），每次收尾时列成清单明确交办。

## 11. 接下来的分阶段执行计划

### 11.1 顺序、范围和完成条件

保留 M0–M6 作为历史功能归属，以下“阶段 0–7”表示新的执行顺序。版本号由实际发布登记并单调递增，不按这里重排的 M 编号机械倒推。每一阶段单独形成可验收候选版；完成前置出口后再开启依赖它的新功能。

| 阶段 | 目标 | 对应原计划 | 出口 |
|---|---|---|---|
| 0 | 明确当前版本与验收基线 | 工程治理 | 当前正式/体验/后端/代码对应清楚，复现与测试数据准备好 |
| 1 | 保证账号、作答和评分正确 | M0 核心 + M6 部分弱网 | 无串账号、串卷、重复扣分；退回重交和合班批阅闭环 |
| 2 | 通知能到达、失败可解释可恢复 | M1 | 三类消息真机通过，业务请求不等待微信批量发送 |
| 3 | 课堂和学习结果可稳定使用 | M2 + M3 | 双角色实课、跨端数据和目标并发验收通过 |
| 4 | 完成教师每天高频移动工作 | 提前 M5 | 看安排→看未交→催交→批阅→看结果完整通过 |
| 5 | 接通有上下文且可恢复的 AI 助手 | M4 | 多轮问答、历史恢复、权限与用量闭环 |
| 6 | 完成移动体验及材料轻浏览 | M6 | 弱网/分享/暗色/长列表/材料范围内均可用 |
| 7 | 完成正式发布和使用反馈闭环 | 各里程碑共同收尾 | 审核发布记录完整，观察期指标和回滚验证完成 |

阶段 4 提前于 AI 的理由：它直接复用已稳定的课表、议程、催交与批阅，覆盖教师每日高频动作；AI 的传输、恢复、成本验收需要额外工作。若后续教学安排要求 AI 优先，可交换 4/5，但阶段 0–3 的正确性与验收前置不变。

### 阶段 0：版本、样本与验收基线

**要完成的内容**

1. 建立一条版本记录：Git commit、构建标识、后端部署版本、小程序上传版本、体验版、正式版、微信基础库、审核/发布时间及验收人。无法核对的字段明确写“待核验”。
2. 对账原 M0–M3 已勾选开发项与未勾选出口，核验现有正式版和体验版。纠正旧文档中“三 tab、通知未做、课堂零覆盖、签到待做”等过期现状。
3. 准备隔离测试数据：教师 A/B；学生 A/B/合班学生/无权限学生/停用学生；主班与挂链班；平时作业、期中、期末、退回、迟交、缺交记零、小组互评和未发布成绩样本。样本不进入正式成绩、积分统计。
4. 将现有 40+6 项专项测试、类型检查和构建接入统一验证入口。审查 48 个非 MP 路由差异后再更新全站快照，保留审查依据。

**验收方式与通过标准**

- 各版本字段有后台或部署证据；正式版与候选版的学生、教师入口各抽查一次，不把本地构建成功写成已发布。
- 阶段 1 的关键问题可在测试样本或受控慢网下复现并记录“预期/实际”，不对真实学生试写成绩。
- 专项测试、类型、构建可重复运行；全站路由快照要么完成审查更新后通过，要么保留明确未解决项，正式发布前必须收口。

**交付物**：版本对照记录、角色/业务样本清单、复现记录、统一验证命令。

### 阶段 1：核心业务正确性与数据隔离

**要完成的内容**

1. 批阅表单始终绑定 submissionId 与成绩修订标识；切换时清旧数据、禁用加载中的保存；丢弃过期响应。保存时再次校验“表单所属提交=当前提交”，处理同时编辑的版本冲突。
2. 区分“教师给出的原始分”和“迟交处理后的最终分”。评分输入使用原始分，最终分和扣分说明用于展示；只改评语不改变分数结果。空值必须拒绝，主动输入 0 才表示零分。
3. 草稿按环境、角色、用户、任务和必要的作答轮次隔离；旧的无账号草稿不自动恢复给未知用户。统一退出、换绑、401 时的内存状态和私有缓存处理，保留同账号允许恢复的草稿。
4. 复用共用身份校验，使停用、删除、退出、解绑、换绑在 MP 专用接口和共享 API 上一致；明确多微信绑定策略，补票据消费/重绑后旧会话失效规则和对应测试。
5. 作答开关消费服务端重交权限、窗口和状态，不能只凭“有无答卷”决定；完成退回说明、剩余时间、重交入口、新旧答卷展示和再次批阅。
6. 教师进度、批阅、未交名单与催交对象统一复用课堂成员口径，覆盖主班、挂链班及停用/退出成员策略。
7. 上传中禁止提前提交，文本/附件保存状态清楚；区分“服务端拒绝”和“请求超时但结果未知”，重试前查询服务端状态，避免重复提交。考试倒计时回前台时以服务端时间校准。
8. 建立统一登录守卫：通知/分享直达二级页也能恢复会话；过期后只触发一次登录流程，成功后回到原目标，并重新校验该目标的角色与权限。

**验收方式与通过标准**

- **批阅竞态**：人工延迟 A/B/C 三份答卷响应并倒序返回，连续切人和保存；每次实际写入的提交 ID、分数、评语都与屏幕当前对象相符，加载中不能提交旧数据。
- **迟交回归**：原分 80、固定扣 10，首次保存为 70；重开只改评语、再次保存仍为 70；主动改原分为 90 后最终为 80。空输入拒绝，明确输入 0 正常按既定政策处理。
- **账号隔离**：A 留草稿退出，B 登录同一任务不能看到 A 文本或附件；A 返回后按保留策略恢复自己的内容。停用账号在 MP/共享 API 均被阻止；换绑后旧会话行为符合规则。
- **重交闭环**：学生提交→教师 Web 退回→学生小程序查看原因并重交→教师小程序批改→两端显示最新有效结果。覆盖窗口过期与旧卷不可再改分。
- **合班对账**：主班、挂链班学生均在进度与批阅队列；名单、应交、已交、待批、催交对象与 Web 使用同一成员口径。
- **弱网提交**：上传未完、断网、超时重试、切后台、计时到期分别验收；允许的重试只产生一份有效提交，草稿与附件不静默丢失。

**出口**：C01–C06、C11 对应问题关闭；上述核心用例全部通过，包含真实 PostgreSQL 和至少 iOS/Android 各一台真机。剩余通知、课堂和结果投影问题继续由阶段 2/3 收口。

### 阶段 2：订阅消息可靠性与消息入口

**要完成的内容**

1. 把截止、催交、批改通知收敛到持久化发送任务：业务短事务只记录事件和待发任务，复用已有 scheduler/任务执行机制；外部微信请求移出主业务事务。
2. 发送状态至少区分待发送、处理中、成功、无授权、暂时失败、永久失败、结果未知；记录事件键、次数、下一次尝试时间、错误类别和租约/处理时间，支持重启恢复与多 worker 原子领取。
3. 调整授权、额度与去重顺序；无绑定/无授权不伪记成功，临时错误按明确策略恢复。授权上报使用去重标识及原子更新，防止重报虚增、并发丢失；台账不能当成微信真实授权的绝对真源。
4. 对超时但可能已送达的情况记录“结果未知”，明确重试策略，不宣称跨网络绝对一次送达。明确失败才能按策略退还/恢复额度；用户拒收后停止无效重试。
5. 在任务页提供用户主动点击的提醒入口；保留提交时的批改结果提醒。拒绝授权不得阻碍提交；首次进入、未预取模板、授权上报断网都有可恢复路径。
6. 催交返回任务进度和发送统计：成功/无授权/失败/处理中分别展示。通知落到准确任务或成绩结果；消息中心补正文展开和历史分页，不能只有两行摘要，未读/已读跨端一致。

**验收方式与通过标准**

- 真机分别验收“截止提醒、教师催交、批改完成”，点击后经冷启动或重新登录仍到正确任务；权限不符时显示明确提示。
- 测试未授权、拒收、模板配置异常、token 过期、微信 5xx、网络超时、服务重启和重复事件；成功记录不重复发送，暂时失败可恢复，未知结果可追踪，无授权不会被显示成送达。
- 在 PostgreSQL 多 worker 下同时领取同一事件、同时上报和消费额度：无重复成功处理、无负额度、无丢失更新；外部调用超时不长时间占用业务事务。
- 模拟微信每次慢响应 8 秒：提交/批改仍按本身性能预算完成，批量催交接口目标 p95≤1 秒返回受理结果；发送结果随后可查询。
- 用测试时间/隔离样本覆盖 24h、2h 两档和重复扫描，不需要对真实学生反复发送通知来验证。
- 超过 150 条消息仍可分页查看，长通知可读全文；标记已读失败不得伪装为服务端已保存。

**出口**：M1 三类真机清单通过，C07/C08 关闭，有可查发送记录和恢复证据。统计须区分接口受理、微信接口返回成功、用户点击，不能把三者混称“已读”。

### 阶段 3：课堂现场、学习结果与容量验收

**要完成的内容**

1. 修正随堂测选项与正确答案的绑定，采用稳定选项 ID 或在过滤时一并映射；空选项、改顺序、选中空项都有校验。
2. 统一课堂快照权限与合班成员；覆盖投票草稿/进行中/结束、单多选/改票、结果可见性、匿名提问、求助取消和教师已解答状态。
3. 保留前台轮询，但增加在途互斥、退避和抖动；页面隐藏停止新轮询，恢复时先刷新；必要时聚合快照、缓存静态信息、减少每次全量返回。不先假定必须改 WebSocket。
4. 成绩单、错题本、任务详情和教师统计统一读取有效成绩与发布状态；覆盖重批保留旧成绩、迟交、小组揭晓、缺交零分和退回。指标明确学期/课堂/课程维度。
5. 任务总计数独立于分页，进行中任务优先按截止呈现；历史按学期、课堂、状态分页。错题和成绩等长列表按数据规模评估分页与增量加载。
6. 建立一堂课的端到端验收和容量基线，观察接口耗时、错误率、数据库慢查询/连接、CPU/内存和已有 Web 提交/批改耗时。

**验收方式与通过标准**

- 教师发起题目→主班与合班学生作答→教师看到计数/正确率；中间留空选项、删除选项后正确答案仍准确。
- 教师开始投票→学生投票/改票→按规则显示结果→教师结束；学生举手/求助→教师看到→学生取消后移除；其他课堂用户不可读取/操作。
- 学生交作业→教师批改→学生查看结果、成绩单和错题；同一测试数据与 Web 逐条核对。未发布/未揭晓成绩不泄露，缺交零分不冒充提交过答卷。
- 建立至少 250 条历史任务，故意保留一条很早创建但仍进行中的任务：该任务在进行中可见，首页计数等于全量状态聚合。
- 按 50→100→200 在线用户递增测试；200 人现场页的理论快照请求量约为 `200 × 2 ÷ 8 = 50 次/秒`，另外叠加真实投票、作答与其他 Web 请求。该值是请求量估算，不能当作已具备容量。
- 建议首轮性能出口：普通读取 p95≤1 秒、写操作受理 p95≤2 秒、非预期 5xx<0.5%，无丢失/重复有效提交；已有 Web 关键路径相对基线退化≤20%；课堂变化在约定一个轮询周期加网络时间内可见。若环境不能满足，优化或限定试点规模，不直接扩大。
- 切后台后无新轮询发出，回前台恢复；连续弱网不叠加无限请求，不以失败结果清空已有有效内容。

**出口**：C09/C10/C12 关闭，M2、M3 真机验收勾选，容量报告给出经过验证的并行课堂/人数上限。200 人是测试目标，实际教学需要更大规模时按峰值加余量重定目标。

### 阶段 4：教师移动工作台（M5 提前）

**要完成的内容**

1. 工作台以“今天安排、待批阅、待催交”组织，不重复堆入口；课表提供今天/本周列表，显示节次、教室、课程、班级和调停课状态。
2. 复用统一课表和议程服务，加入监考/考试安排；时间、时区、调课更新与 Web 一致。
3. 跨作业未交中心按课堂、任务、截止状态筛选；教师确认接收范围后批量催交，复用阶段 2 的异步任务与去重规则。
4. 从待批卡进入当前提交/下一份，返回后保留列表位置与筛选；保存后首页待批数、任务统计同步更新。
5. 补齐教师移动批阅的后续动作：批量 AI 批改的排队/进行中/失败/完成状态可查；退回重交、缺交记零的撤销或更正均复用现有权限与业务规则。页面承诺“可撤销”时必须有实际可达入口。

**验收方式与通过标准**

- 一位教师完成“早上看当天课表和监考→课间查看未交并催交→晚上顺序批阅两份→回工作台核对待办减少”。
- 调课、停课、跨周、无课/无监考、无待批均有正确结果和空态；两位教师只看到各自有权访问的安排与学生。
- 同一学生在多个任务中的催交遵循每任务规则；已提交/已停用/已截止不再允许催交的对象按服务端策略排除，反复点击不增加重复任务。
- 首屏和批量受理达到阶段 3 的预算，工作台与 Web 数字一致，所有已开放入口可走完业务。
- AI 批改失败可找到原因和允许的重试入口；教师退回后学生能重交，缺交记零后按规则更正，任务统计、成绩单和修订记录同步更新。

**出口**：M5 移动日常场景通过，教师不再依赖预告占位完成这组高频操作。

### 阶段 5：AI 学习助手（M4）

**要完成的内容**

1. 先验证现有 `/api/ai/chat/sessions/*`、会话创建、历史和 `/api/ai/chat` 对 MP Bearer、课程权限及会话归属的支持；复用现有聊天、学业上下文、模型路由和记录体系，不新建另一套 AI 业务。
2. 先做真实设备传输验证，再选分块请求或任务轮询。原 §5 的“uni.request 不支持流式”表述过于绝对：官方文档已列出微信端 `enableChunked` 及 `RequestTask.onChunkReceived`。仍需验证本项目锁定的 uni-app 版本、微信基础库、UTF-8 跨块处理、nginx 缓冲与前后台中断；验证失败才选受控轮询降级。[uni-app 请求文档](https://uniapp.dcloud.net.cn/api/request/request.html)
3. 先交付文本多轮对话、课程选择、历史恢复、轻量 Markdown/代码展示、生成中/失败/停止状态；附件问答作为后续独立范围，不与首批混在一起。
4. 绑定用户/课堂/会话和客户端消息 ID，断网重试先查询已受理状态；停止或离开后如何保存结果有明确规则，不因重复点击重复生成或记账。
5. 沿用平台 AI 用量/预算和业务优先级，设置可配置频控与并发上限；普通聊天高峰不能挤占批改、考试等高优先任务。用量上限及失败原因对用户可理解。

**验收方式与通过标准**

- 学生选课程进行至少三轮带学习上下文的问答；退出重进能恢复历史，课程/账号切换不串上下文；不能读取他人会话或不属于自己的班级资料。
- 覆盖长回答、代码、中文跨块、生成中切后台、断网恢复、主动停止、请求超时与重复点击；同一用户操作只产生预期的一次生成任务和一次对应记账。
- 测试频控/余额不足/模型失败，UI 有明确结果，已有聊天记录保留；真实用量与平台台账、模型路由结果可对账。
- 至少一台 iOS、一台 Android 完成传输验证；记录首反馈和完成耗时，按使用模型和网络制定预算，不把模型慢响应算作普通 CRUD 接口 SLA。

**出口**：M4 多轮问答、恢复、权限和用量验收通过；若流式兼容尚未通过，必须有已验证的降级方式后再开放入口。

### 阶段 6：移动体验、分享和学习材料

**要完成的内容**

1. 暗色模式沿用全局视觉令牌，覆盖导航、tab、表单、弹层、分数状态和图表；低性能设备对玻璃效果可降级，触控区域、字号和键盘遮挡一起检查。
2. 系统性弱网处理：读取有限重试、手动重试/下拉刷新、离线提示、缓存新鲜度；写入按幂等与状态查询恢复，不做无条件 POST 自动重放。草稿、图片失败、401、加载与空态采用一致语言。
3. 任务/投票分享保留课堂和对象上下文，配合阶段 1 的登录后回跳；目标不存在、已结束、无权限都有准确说明，分享不携带答案、token 或私有成绩。
4. 材料轻浏览首批明确支持 Markdown、图片及可由原生预览打开的 PDF/Office；复用材料权限和鉴权下载/预览。若记录学习进度，必须复用现有进度契约，未达到条件不能自动记完成。
5. HTML 互动包、复杂文档和绘图题分别评估移动方案；本期不支持的内容在学生开始任务前说明并提供可行入口，不临近提交才提示。Canvas 绘图如启用，另验收保存、恢复、导出、批阅与无障碍替代方式。
6. 记录包体、冷启动、首屏、长列表和图片内存基线；按需拆普通分包，优先隔离 AI/材料等低频页并保留旧深链兼容，验证低端机收益后再扩展。不要为追求最新能力顺带升级锁定依赖。
7. 任务说明、题干、教师批语和 AI 共用受控的 Markdown/富文本渲染约定，逐项定义图片、公式、代码块、链接的支持范围；影响学生读懂当前试题的渲染缺陷前移到阶段 1/3，不能等到体验阶段才处理。

**验收方式与通过标准**

- iOS/Android、小屏/大字模式、浅色/深色、键盘弹起各走一次核心流程，无遮挡、不可读状态或无法点击的主操作。
- 断网、恢复、图片失败、附件过期、401 重登录和写入未知状态全部有明确下一步；用户已输入内容按既定恢复策略保留。
- 分享给已登录同班、未登录同班、其他课堂用户分别验证：前两者按权限到目标，后者不泄露任务内容。
- Markdown、图片、PDF、Office 和无权限材料样本逐类验证；记录各格式实际支持范围，浏览与学习进度与 Web 对账。
- 与阶段 0 构建/启动基线比较，记录真实上传包信息；冷启动和首屏性能达到评审确定的设备预算，新增分包后历史通知链接仍能打开。

**出口**：M6 已承诺范围全部验收；绘图、复杂 HTML 等尚未选定方案的条目明确留在候选池，不把“已评估”标成“已实现”。

### 阶段 7：正式发布、监测和迭代闭环

**要完成的内容**

1. 每个候选版执行变更相关回归、MP 专项、类型、构建、路由契约、PostgreSQL 和真机验证；无关全站回归失败也要记录归属与处理，不伪报全绿。
2. 后端变更先跑既有部署 DryRun，完成兼容部署与生产服务检查，再上传匹配的小程序候选版。保留旧正式版客户端对新后端的兼容；数据库迁移先扩展再切换，支持代码回滚。
3. 核对合法域名、TLS、隐私说明与实际权限调用、订阅模板、审核账号及类目/品牌信息；以当次后台显示和平台要求为准。审核账号使用隔离数据，完成复审需求后再按策略停用，不能误删真实学生记录。
4. 建立消息授权/发送状态、提交成功/失败、草稿恢复、批阅保存失败、课堂参与、JS 异常与关键接口耗时指标；用户数据不进入无权限日志。隐私与平台后台核验列为发版任务，不预设本轮有违规。
5. 先做一个真实课堂的小范围试点，再按阶段 3 已验证的容量扩大；记录观察期、反馈、责任人和回滚触发条件。

**验收方式与通过标准**

- 正式版有版本号、Git commit、后端版本、审核/发布证据与本版真机清单；“上传成功、体验验收、审核通过、正式发布”分别记录。
- 试点至少覆盖一堂真实课和一个作业周期；发布后观察 7 天。账号/成绩错误为零，提交无丢失，通知失败可解释可恢复；接口和课堂容量达到阶段 3 约定的指标。
- 在预发布环境演练回滚，旧客户端继续登录、提交和查看结果，后台待发任务不因回滚重复领取；记录恢复耗时。无需为验收而故意中断生产。
- 所有 P0/P1 和业务必经阻塞关闭；非阻塞视觉问题可带明确范围、负责人和版本进入后续迭代。

**出口**：形成可追溯正式版本和使用数据，按证据更新本文里程碑出口，而非仅勾“代码完成”。

## 12. 通用验收纪律与最近一轮任务单

### 12.1 每阶段必须留下的证据

每条验收记录至少包含：用例 ID、客户端版本/commit、后端版本、角色和样本 ID、设备/微信基础库/网络条件、操作步骤、预期结果、实际结果、截图或短视频、必要的 API/数据库对账、执行人和日期。失败项必须能链接到修复提交及重验记录。

本地单测、PostgreSQL 集成、真实设备交互、生产只读验证分别记录；任何一种都不能代替其余必需层。测试数据不得混入正式成绩、积分与通知对象。每阶段结束才勾选出口，不用代码行数或勾选比例推算“总体完成百分比”。

### 12.2 建议立即开始的工作顺序

1. **本轮第一批**：阶段 0 的版本与样本核对；修 C01 批阅串卷、C02 迟交重复扣分、C03 草稿账号隔离、C04 停用身份校验。

3. **下一候选版**：阶段 2 通知后台化、状态/额度/去重修复及三类真机送达。
