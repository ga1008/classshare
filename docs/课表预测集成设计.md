# 教务课表与调停课预测集成设计

日期：2026-09-19。状态：已按本设计实施并完成本地及原生 PostgreSQL 业务验证；发布结果记录在文末。本文保留实施前调查依据，实际协议以当日真实浏览器核验及解析器合同为准。

本设计针对正式 LanShare 功能。此前的独立 HTML 日历继续作为独立交付，不作为线上数据库真源，不被正式页面引用。本文只规定必要的课表、申请、课次身份和共享交互改进，不扩展到教务申请提交、审批或全校排课。

## 1. 用户需求及验收对应

| 编号 | 用户要求 | 实施约束与验收 |

| R1 | 搜索栏附近提供同步按钮，读取教务系统课表及调停课申请。 | 教师可用；明确选择学年学期后同步同一学期的两类数据，显示阶段、时间和结果。学生只读同一结果。保留原智慧课堂同步入口及接口兼容。 |
| R2 | 待通过的原课程保留原底色，外侧虚线与卡片之间有 4px 透明间隙，并标记调课、停课或更换教室；新位置使用原色 25% 与白色 75% 混合的不透明浅色底、深色文字，并标记“正在申请变更”；同时段仅换教室只显示一张卡。 | 仅 `pending` 申请启用这些交互。停课不生成虚构目标卡；仅换教室不生成重叠的第二张卡，卡内可看原/拟教室。原卡配色、课程信息、点击行为保留。 |

| R7 | 明确学年学期；发现新学期自动建库初始化，再生成，所有同步数据的学期一致。 | 复用统一学期身份，不按当前日期猜远端参数，不把缺少学期的响应当作当前学期。经核验的新学期自动幂等初始化，正式课表、申请和校历必须属于同一目标学期。 |
| R8 | 允许必要重构，同时保留现有功能。 | 修复课次身份重排风险，保留智慧课堂、历史学期、合班、材料、学习进度、签到和现有手工编辑保护；不整体重写业务。 |
| R9 | 所有 3D 课表入口复用同一组件。 | 教师首页、课时统计/课表管理页、学生首页统一使用 `course_schedule_deck.js` 的状态、投影样式和跳转逻辑。调用方只提供数据、权限和同步回调。 |
| R10 | 业务完整闭环。 | 覆盖待审、通过、拒绝、撤销、状态未知、读取失败、目标未生效、冲突、再次调课、旧批次迟到及重复同步。保留可核对来源和旧的有效结果。 |

### 1.1 不变量

1. 正式课表与预测是不同事实。只有待通过申请产生预测，预测不计入正式课时，不生成真实课次。
2. `session_id` 表示一堂具体教学内容及其历史业务记录；调整日期不能改变它，也不能把另一堂课的内容放进该 ID。
3. `order_index` 是现有教学序列，不因调课按新日期整体重新编号。按日期展示时允许课次序号不连续或不单调。
4. 同一合班课不能按行政班拆成多条真实课程。已审批且已反映到课表的申请不能重复应用。
5. 调整只允许修改精确识别的日程字段。标题、内容、课程模板、主材料、多材料绑定及历史记录默认保持原值。
6. 无完整、同学期、通过校验的新快照时，继续使用上次有效数据；空响应、登录页、缺页和解析失败都不是“没有课程”。
7. 学生只能看到已授权课堂的课程和相关变更，不直接读取教师完整教务申请列表。

## 2. 已调查的现有链路与风险

### 2.1 现有结构

| 层 | 现有对象/代码 | 与本次相关的事实 |
|---|---|---|
| 学期 | `academic_semesters`、`semester_identity_service.py` | 有统一的学年学期规范名及 `xnm/xqm` 转换，应复用。 |
| 教务周期规则 | `teacher_academic_course_sync_items` | 一条规则包含周次、星期、节次、教学班和地点。 |
| 教务逐次排课 | `teacher_academic_course_session_occurrences` | 保存实际日期和节次；唯一键含日期、节次、地点，不适合代表跨调整的稳定课次。 |
| 真实课堂课次 | `class_offering_sessions` | `id` 被材料、进度、生成任务、考勤等引用；唯一约束为课堂与 `order_index`。 |
| 智慧课堂课表 | `smart_classroom_course_schedule_items/meta` | 现有教师 3D 课表优先读取此源。它与教务课表不是同一数据源。 |
| 教师 overview | `smart_classroom_schedule_sync_service.build_teacher_course_schedule_overview` | 智慧课堂无该学期数据时才回退平台课次；回退聚合后丢失具体 session ID。 |
| 学生 overview | `student_course_schedule_service.build_student_course_schedule_overview` | 从授权课堂真实课次生成，以实际日期为准，排除已取消课次。 |
| 共享周卡 | `static/js/course_schedule_deck.js` | 被教师首页、管理课表页和学生首页复用，目前链接主要到课堂，未建立本次所需的精确课次深链合同。 |

可复核代码位置（以设计时版本为准）：

- `academic_course_sync_service.py:2206—2214、2369—2378`：同步删除重建规则和 occurrence；相关自增 ID 会变化。
- `course_planning_service.py:1422—1457、1484`：先按日期排序 occurrence，再按下标绑定模板，重新生成 `order_index`。
- `course_planning_service.py:297—399`：按课堂＋序号 upsert，会更新标题、内容、日期和材料等。
- `academic_course_sync_service.py:2116—2128`：教务同步直接调用上述生成和替换，虽有 `preserve_removed=True`，仍不能保证跨日期调整时身份不变。
- `academic_course_sync_service.py:1969—2026`：模板保护仅判断自动来源及模板主材料；不能直接替代真实 session 上的多材料/学习/考勤保护。
- `academic_sync_reconciliation_service.py:588—616`：排课预览主要比较课次数，等量调课可能不产生排课差异项。
- `academic_sync_reconciliation_service.py:904—941`：漂移检测覆盖课程、班级字段，不覆盖真实 session 日程及材料关联。
- `smart_classroom_schedule_sync_service.py:1276—1368、1459—1469`：教师课表回退源按课堂、星期、节次、教室聚合。
- `smart_classroom_schedule_sync_service.py:979—1015`：共享周卡数据生成需显式保留新增的课次和投影字段。
- `student_course_schedule_service.py:105—110、176—184`：已有 session ID，但尚未形成精确课次入口。
- `classes_courses_offerings.py:351—387`：手工编辑已有课程→课堂→session 锁序及预览 revision 校验，可复用其原则。
- `offering_plan_edit_service.py:7—15`：SQLite 与 PostgreSQL 的行锁适配；`db/connection.py:35—44` 的 `begin_immediate_transaction` 在 PostgreSQL 下不提供额外串行锁。

### 2.2 必须先消除的身份错配

假设已有课程 A、B、C 对应 session 101、102、103，分别在 9/20、9/26、9/27。若 A 调至 10/11，按新日期重排会把 session 101 放到 B 的原日期，session 103 放到 A 的目标日期。外键仍然存在，但历史记录代表的课已经错了。若取消 A，按新序号 upsert 则可能取消末尾 C，错误更隐蔽。

因此，不能把“原事实＋预测目标”一起交给现有 `build_academic_offering_session_plan`，也不能在正式通过后再次用这条整体排序路径覆盖已有课堂。

## 3. 总体方案

采用“来源批次 → 正式事实与申请事实 → 稳定课次绑定 → 共享展示投影”的四层结构。

```text
教师显式选择学年学期
  └─ 查询教务课表、调停课列表/详情、必要校历
       └─ 验证完整性、目标学期、状态和字段
            └─ 原子发布该教师/学期的新来源批次
                 ├─ 正式课位 → 精确绑定原 session → 仅更新已生效日程
                 └─ pending 申请 → 原位置标记 / 目标预测投影
                      └─ 教师与授权学生 overview
                           └─ 同一个 3D 组件 → 同一个真实 session
```

新增独立的教务课表同步/投影服务，职责限定为本功能。抓取、解析、持久化、稳定绑定及展示组装拆成清晰函数，不把远端网络请求塞进 overview GET，也不让前端自行合并申请。

教师已完成本学期教务课表同步时，以其有效正式快照作为该学期课表展示源。没有有效教务快照时保留原智慧课堂/平台回退行为，并明确来源。保留未绑定平台课堂的正式教务课程，不因增加精确 session 能力而丢弃原课表条目；这类条目没有可猜测的课次链接。

## 4. 数据模型

以下是逻辑模型，不要求按每一层机械新建表。实施采用精简结构：同步状态/批次、稳定 bindings 和 change links；正式周期/逐次数据与申请结构可存于受限的批次 JSON。只有查询或唯一性确有需要时再拆表。所有时间采用项目现有时区/UTC 约定，远端学期代码单独保存；不保存登录凭据、Cookie、完整无关学生信息或任意原始 HTML。

### 4.1 同步状态与批次

`teacher_academic_schedule_sync_state`：每个教师一行，以 `teacher_id` 为主键。

- 教师级租约覆盖同一账号的所有学期，防止跨学期并发任务互相覆盖同步状态。
- 保存 `last_success_at`、`last_attempt_at`、最近状态和可展示错误摘要。
- `lease_token`、`lease_expires_at` 通过数据库 CAS 获取；默认 600 秒，最大 1800 秒。已过期、被接管或已发布的 token 不能再次发布。
- 网络读取之前提交 claim；发布和释放由 caller 提交。GET 不获得租约。

`teacher_academic_schedule_snapshots`：每个 `(teacher_id, semester_id)` 保存最后一个完整成功批次。

- 保存 revision、发布时刻、publication token；正式课表及本次申请写入 `snapshot_json`。
- `request_history_json` 保留历史申请与 `missing_unconfirmed`；`lessons_json` 保存同批投影，`warnings_json` 保存核对提示。
- `covered_offering_ids_json` 标识本批已覆盖的课堂，即使整门课取消、当前 lessons 为空，学生视图也能移除旧卡。
- 适配器必须核实全部分页和明确学期后才返回；缺页、接口失败、`complete=false` 均不能提交快照。
- 发布以同一事务替换快照与允许更新的日程。失败保留原快照；不保存认证页面、敏感头或无限增长的 HTML 历史。

加上后述 bindings 和 change links，实际共四张新表；没有机械拆分的中间事实表。

### 4.2 正式课位事实

批次 `official` 数据：批次内的一次正式上课位置，作为远端事实，不直接充当课次 ID。可存 JSON 数组，不要求单独 `slots` 表。

- 教师、来源、学期、batch、远端课程 ID/课程号、教学班 ID/名称、行政班组成摘要。
- 实际日期、学期周、星期、开始/结束节次、校区、教室 ID/名称及可证实的作息字段。
- 源规则摘要、来源位置、规范化课位指纹。
- 批次内唯一键必须区分教学班、课程、日期、节次和必要的场地信息；同一合班只保留一次。
- 星期以项目服务层的既定口径明确转换；不得混用 `0—6` 与 `1—7`。

既有 occurrence 可以继续作为业务兼容投影，但不能作为新绑定的唯一依据。避免创建两份互相独立的正式真源：新成功快照负责对齐，旧表由同一事务或同一受控 reconcile 流程派生。

### 4.3 调停课申请事实

批次 `requests` 数据：按远端申请稳定身份归一化，含一对多申请明细。历史批次及必要的缺失记录保存来源历史，不要求单独 `changes/details` 表。

- 唯一键：教师、学校来源、规范学期、远端申请 ID `ttk_id`；展示流水号 `ttk_lsh` 单独保存，不混作主键。
- 适配器 `kind`：`move / cancel / unknown`；展示层的 `room` 由 move 原/目标日期节次相同且教室不同确定，不依赖原因关键词。
- `approval_status`：`draft / pending / approved / returned / rejected / unknown`，另存原状态代码。撤销状态目前未实测，不凭缺失行产生 `withdrawn`。
- 原安排、目标安排分别保存结构化日期、周次、星期、节次、校区及教室；停课的目标为空。
- 远端课程/教学班稳定身份、原因、提交/状态更新时间（仅远端提供时保存），首次发现/最后成功发现时间，最新批次和内容指纹。
- 申请记录保留，不通过“删除该行”表示已审批。是否生成预测由状态和绑定结果决定。
- 经完整成功快照证明不再出现的旧申请，设置 `present_in_latest_snapshot=false` 并停止其 active 预测；保留 `missing/unconfirmed` 历史及上一状态，不把缺失解释为通过或撤销。失败、缺页快照不能执行此处理。
- 明细使用 `ttkxx_id` 稳定标识，不能假设一条申请只有一个原/目标课位。原/目标位及课程绑定均以明细为粒度处理。

### 4.4 稳定课次绑定

`academic_schedule_session_bindings`：长期维持来源课程事件与真实 session 的关系。

- `teacher_id, semester_id, class_offering_id, session_id`。
- 本地稳定 `event_key`，初次绑定后不随调课改变。
- 课程/教学班远端身份、初始课位指纹、当前正式课位指纹、最近确认批次、绑定状态/证据。
- 每个 session 对应一个稳定课程事件；相同远端合班若历史上对应多个独立课堂，允许建立各自的 offering 绑定，不能任意挑一个课堂。
- FK 至真实 session 用保守删除策略，不能因某次 occurrence 重建而级联删除绑定。

`academic_schedule_change_session_links`：申请与上述稳定绑定的关系。

- 唯一键：申请明细、课堂、session；引用稳定绑定。
- 保存 `matched / ambiguous / unmatched / conflict`、用于匹配的原位置指纹及证据摘要。
- 同一 session 可以存在有明确来源的再次调课链。多个仍待审且互相矛盾的目标必须标记冲突，不能凭申请时间或数组顺序擅自选一个执行。

索引至少覆盖教师/学期/批次、教师/学期/审批状态、课堂/session 及远端申请唯一键。读取按授权课堂批量查询；不为每张课程卡执行一次 SQL。

### 4.5 初始化与迁移

通过正式迁移注册新表、索引及版本，不在每次 overview GET 临时建表。SQLite 和 PostgreSQL 同步覆盖唯一约束与索引。

存量绑定回填只做可证明的一一匹配：既有 occurrence 关联、同一教师/学期/课堂/教学班身份和实际课位的唯一匹配，或已核实申请的原/目标对应关系。自增 ID、数组位置、相近日期、同名课程均不能单独作为证据。无法证明的行保留原数据并标记待核对，不重编号、不自动覆盖材料。

## 5. 稳定身份与正式日程对齐算法

1. 读取目标教师/学期的正式快照及所有待审/近期已变更申请；构建远端课程与教学班身份键。
2. 在删除或替换任何 occurrence 之前，读取既有课堂、session 和持久绑定，保留旧课位证据。
3. 优先使用已存在的稳定绑定；其次使用已核验的申请链；最后只接受唯一、严格的同身份课位匹配。
4. 待审申请只绑定原 session、生成展示投影，不改该 session 的正式时间、地点和状态。
5. 已通过申请且新课表目标已出现：把精确绑定的原 session 更新到目标位置。只允许日程字段更新，保留 session ID、`order_index`、模板、标题、内容及全部材料关联。
6. 已通过停课且新正式课表对应原课位已消失：只将对应 session 标记取消，保留历史记录。不能取消末尾序号替代。
7. 正式课表与已批准申请尚不一致：展示正式事实普通卡，撤下 pending 预测，产生明确同步告警；不依据申请擅自变更正式 session。
8. 对于无法通过已知申请解释的正式时间变更，先尝试稳定来源标识或唯一确定性映射；仍不唯一则保留 session 和材料，仅记录待核对差异。
9. 真正新增、且已确定没有历史 session 的正式课次才允许创建。已有教学序列不重排；新身份使用新的稳定 ID。首次初始化没有历史业务的课堂时，可以按初始正式日期建立序列一次。
10. 新批次重复执行必须产生相同绑定及日程；已审批且已在当前课表中的申请仅用于解释和审计，不再追加一次目标课程。

特别处理已核实的官方课表合并时段：当前第 2 周 Python 周日把相邻两堂课合并为 4—7 节的一条规则，但平台语义仍是 4—5 节和 6—7 节两堂课。正式源先保存完整覆盖，再依据已有稳定 session 或已核验申请原/目标的节次边界拆分，保证覆盖集合一致、不重叠、不遗漏。不得把四节合并块直接当作一堂新课，也不能无证据地把任意长时段每两节切分。证据不足时保持正式课表可见并标记未关联，不制造错误 session。

现有整体替换函数继续服务于合法的初次排课和已有受保护的手工编辑流程；教务重新同步已有课堂必须改走身份 reconcile。对于已有真实 session 或业务关联的课程，不再借“模板仍是自动占位”删除重建其模板并顺序覆盖课堂内容。

## 6. 审批与课表状态生命周期

审批状态、课表生效状态和数据新鲜度分别保存，不能用一个 `moved` 布尔值替代。

| 审批状态 | 最新正式课表 | 展示 | 真实 session |
|---|---|---|---|
| pending 调课 | 原安排仍在 | 原普通底色＋外虚线和调课标签；目标使用混白实色底与深色文字；双向互跳。 | 不改正式日程，两卡指向同一 session。 |
| pending 停课 | 原安排仍在 | 原卡外虚线＋停课标签，说明正在申请；无目标卡。 | 保持正式课程与课时。 |
| pending 仅换教室 | 日期节次相同 | 一张原底色卡＋外虚线＋更换教室标签，展示原/拟教室。 | 不改正式教室。 |
| pending | 目标已在课表或原位置缺失，状态矛盾 | 去重事实；只在仍有可靠绑定时标注待审状态与矛盾说明，不制造第二张重复目标卡；需要核验。 | 不猜测批准，不重排或自动取消。 |
| approved | 目标已在正式课表且原事实已正确替换 | 目标普通卡，不保留 pending 虚线、预测和互跳标签。 | 精确更新原 session 日程，ID/内容不变。 |
| approved 停课 | 正式课表已移除对应原课 | 正式课表无该课，审计/历史保留停课记录。 | 精确标记对应 session 取消。 |
| approved | 正式课表尚未反映目标 | 正式事实普通卡＋同步状态告警；**不继续显示待审虚线/预测**。 | 保留原正式日程，等待可靠新课表。 |
| draft / returned / rejected | 任意 | 不产生待审预测，按正式课表普通展示；保留申请审计。 | 不依据未提交/退回/拒绝申请改课。 |
| 完整成功快照中 missing | 最新正式事实可靠 | 停止该申请 active 预测；按正式事实展示，历史保留“缺失，状态未确认”，不伪装撤销。 | 不依据缺失申请擅自搬课。 |
| unknown / 解析不完整 | 不可靠 | 不伪装为 pending 或 approved；保留上一有效展示并标识该次同步失败/状态待核验。 | 不修改。 |
| 网络/登录/限流失败 | 无新有效批次 | 原有效课表继续可用，显示最后成功时间及重试入口。 | 不修改。 |

特殊处理：同一课的多条未决申请、连续改期、多个申请指向同一目标时段、老师或合班学生时段冲突，均记录可解释冲突。预测不阻止查看正式课表，也不能以“全部假设通过”自动执行多个相互矛盾的申请。

## 7. API 与 overview 增量合同

### 7.1 同步入口

新增 `POST /api/manage/academic/course-schedule/academic-sync`，仅教师本人可调用。

请求明确包含 `academic_year`、`academic_term`；可带 `semester_id`、前端上次看到的 revision 或幂等请求标识。两种学期表示同时存在时必须验证一致。普通点击按所选学期同步，不能忽略它并自动抓当前学期。

响应统一返回状态、实际同步学期、批次/修订号、最近成功时间、课表/申请数量、变更/绑定/未匹配统计及同一批次生成的 overview。若执行进入现有后台任务，应返回任务 ID 并采用同一后台任务机制报告进度，不另造轮询体系。

继续保留现有 `/api/manage/academic/course-schedule/sync` 及 `/api/manage/teaching/course-schedule/sync` 的智慧课堂语义。新按钮标注“同步教务课表”，不能把旧接口静默改成不同来源。

### 7.2 学期发现和初始化

1. 页面展示规范学期选择及当前有效来源。已有本地学期可以立即选择；未在本地出现的学期通过明确的教务学期发现操作获取真实选项。
2. 若需要新增发现接口，使用受认证的显式 POST，不在普通 overview GET 中自动登录教务。实现前复核现有同步对话框是否能复用该能力，避免重复交互。
3. 使用 `semester_identity_service` 规范化身份及 `as_xnm_xqm`，禁止把展示学期序号直接当远端参数。
4. 从教务真实校历确认学期起止、第一周周一及教学周数，再幂等创建或复用同校学期。已有同身份学期的人工配置存在冲突时记录差异，不随意覆盖。
5. 新学期只初始化已确认的学期与日历元数据；发现学期不意味着自动新建课程、课堂、学生或重排旧课。
6. 学期缺少可靠日期时不编造学期锚点，不生成标为精确日期的预测。显示可操作的同步错误，保留旧有效结果。

### 7.3 overview 字段

保留现有 `terms / selected_term / filters / summary / courses / weeks / section_range` 字段及未采用新功能的行为。新增字段以可选字段兼容。

顶层建议：

- `schedule_source`、`sync_state`（最近成功/尝试时间、状态、批次、revision、错误摘要）。
- `change_summary`（待审各类型数量、已批准待课表生效、未匹配/冲突数量）。
- `summary` 增加明确正式课时与预测数量；原正式课时统计不因增加投影而翻倍。

每张周卡 lesson 使用以下统一增量合同，不再并行引入 `slot_key`、`session_url` 等同义字段：

| 字段 | 含义 |
|---|---|
| `event_key` | 本次展示位置的稳定唯一键，区分原卡与目标投影；两者通过同一 session 和 adjustment 关联。 |
| `session_id` | 已验证的真实 session；无法唯一绑定时为空。 |
| `session_no` / `session_total` | 真实 session 的稳定 order_index 与课堂已存在身份总数，保留已取消的历史身份，不按调整后日期重新编号。 |
| `binding_status` | `bound` 或 `unresolved`；无法匹配时提供提示，不猜测链接。 |
| `class_offering_id` | 已授权对应课堂。 |
| `classroom_url` | 已有关联时直接带 `?session_id=...` 的精确课次深链，保持旧字段消费者兼容。 |
| `actual_date` | 正式卡的实际日期或预测卡的拟日期；学期周及星期由同一锚点计算。 |
| `counts_towards_total` | 正式统计边界；预测固定为 false，正式事实为 true。 |
| `adjustment` | 仅 pending 提供下述结构；其他状态不保留 pending 交互对象。 |

```text
adjustment: {
  request_id,
  kind: move | cancel | room,
  phase: pending,
  endpoint: original | proposed,
  counterpart_event_key,
  counterpart_week_index,
  original: {date, sections, room},
  proposed: null | {date, sections, room}
}
```

停课及同位置换教室没有第二个位置，counterpart 字段为空。身份未匹配或冲突通过 overview 同步/告警摘要说明，不生成猜测的课次链接。正式事实存在但没有本地课堂时允许保留原未关联入口；能精准绑定的 pending 原/目标必须共享同一个 `session_id` 和 `classroom_url`。

`id` 继续兼容旧消费者，但不能再让一个聚合周期条目的 ID 被当成每一堂课的真实 session ID。`session_no` 从实际绑定 session 的稳定教学序列取得，不能从投影数组排序产生。

先同步快照、后新建课堂时，下次 GET 保持纯读，不偷偷重建绑定。创建完成后需要再次同步教务课表建立精确关联，界面应明确提示这一操作。

## 8. 全入口交互与深链

### 8.1 入口复用

- `static/js/dashboard.js`：教师首页，搜索栏附近加入有权限的同步入口，调用共享同步控制器。
- `static/js/manage_course_schedule.js` 与相应管理页面：接入相同来源、学期及同步结果，保留原统计和智慧课堂同步。
- `static/js/student_dashboard_schedule.js`：复用相同 pending 投影表现，不提供教师同步权限。
- `static/js/course_schedule_deck.js`：唯一负责虚线、4px 间隙、混白实色目标、标签互跳、跨周定位、高亮、键盘及触屏。

需要搜索并验证所有 `createScheduleDeck` 调用，避免首页更新而管理页仍使用旧合同。已有模块缓存版本一起更新，不能仅修改源码而页面继续使用旧资源。

### 8.2 卡片交互细节

外虚线通过独立伪元素或外层描边实现，边框与原卡之间保留真实 4px 透明空隙；不改变原卡底色和可点击区域。虚线及标签不被周网格裁切，不遮挡相邻节次。

课程主体点击进入真实课次；变更标签点击只执行定位/对照，阻止事件穿透。标签不能嵌套成无效的链接/按钮结构。目标周渲染完成后根据 `event_key` 聚焦和短暂高亮，不用固定延迟猜 DOM 是否可用。

跨周互跳保留课程/班级筛选与当前学期。筛选会隐藏关联目标时，优先在相同课程过滤范围内定位；确实无法展示时明确说明，不偷偷清空所有筛选。使用 `prefers-reduced-motion` 时减少动画，高亮不只依赖颜色。

同时段换教室一张卡；停课无目标卡；目标已有正式事实时不重复画同一课程。正式卡与预测卡在相同时段涉及不同课程时必须可逐项访问，不让后渲染的卡完全遮住另一张。

### 8.3 精确课次深链

建议链接为 `/classroom/{offering_id}?session_id={session_id}`，最终名称与现有课堂工作区入口约定核对后统一。

服务端先执行课堂权限检查，再验证 session 的 `class_offering_id`，将对应教学序列/课次信息交给工作区初始化。不能只在前端 URL 中放一个 ID 后让页面静默定位到“今天的课”。非法、他课或已失效 ID 给出明确结果，不回退到一堂看似正确但实际无关的课。

原卡、预测卡、周明细的链接必须完全指向同一 session。课堂内部、材料阅读、任务、考勤仍使用原 session 作用域，不以预测日期创建临时业务空间。

## 9. 并发、事务及失败保护

1. 通过教师＋来源＋规范学期级租约或 CAS 限制并行同步；两次点击返回已有任务/明确忙碌状态，不能各自删除重建同一学期。
2. 网络抓取、详情分页和解析在数据库写事务外完成，限制超时、重试和并发数，不占长事务等待教务响应。
3. 同步以开始时的 `revision` 和唯一 token 为基础。提交前锁定同步状态，确认 token、租约和 revision 有效；晚到的旧批次标记 superseded，不覆盖新事实。
4. 写入事务按现有课程→课堂→session 顺序锁定受影响资源，稳定顺序排序；锁后重读身份、日程和材料保护状态。
5. 正式快照、申请状态、绑定、允许的日程更新及 active batch 切换同事务提交；失败整体回滚。不能出现申请已批准但卡片仍基于前一批次的混合结果。
6. 预测展示由有效快照派生。overview 只读、批量查询、无外部网络、无自动建表、无课次更新。
7. 原 occurrence 的兼容重建必须在稳定绑定捕获之后，且不能顺带触发按日期重编号。其他同步入口也要经过同一身份 reconcile，防止下次旧同步又把本次保护破坏。
8. 手工编辑和材料绑定并发时，使用既有锁序和 revision；只调日程不写回旧的标题、内容或材料快照。遇到人工日程已变更，记录待核对冲突，不以陈旧申请覆盖。
9. 完整成功但明确无课程/无申请与“抓取失败为空”要有不同结果。只有协议明确证明完整空集才允许更新事实；即使如此也不能删除历史 session 或材料。
10. 失败状态仅更新尝试记录与可读错误，继续提供上一有效快照。前端始终显示数据时间，不用旧数据伪装为刚同步成功。

## 10. 权限与性能

教师 ID 仅取会话，不接受客户端任意指定。学期属于教师可访问的学校范围；课程、教学班、课堂、session 匹配全过程都包含教师和学期约束。

学生查询复用有效学籍、主班及合班成员关系。通过已授权 offering ID 批量取绑定和申请摘要，不返回其他课程申请、完整教师源数据或无关班级个人资料。课次深链在服务器再次验证权限。

班级关联变化立即影响学生可见范围，不能依赖浏览器缓存长期保留权限。相关 API 使用既有私有缓存/无缓存约定，缓存键至少含身份、学期和有效 revision。

一次 overview 的 SQL 次数应固定或按必要批次增长，不随周卡数量线性增加。全学期只在后端展开一次；新增预测数量由待审申请决定。教师同学期同步限流，详情使用小并发或顺序请求，不持续轰击教务系统。

### 11.4 尚需核验的边界

已通过申请何时与正式课表一致、明确撤销是否有其他协议证据、新学期可选项与校历查询合同，以及不在已确认类别内的申请仍需针对性核验。解析器应有版本化脱敏样本和失败断言；原因文本仅作说明，不能依据“国庆”“考试”等词推断日期、类型或状态。

## 12. 测试与验收

### 12.1 解析和身份

- 同一目标学期的课表、列表、详情及校历一致；显式选择历史学期绝不被当前学期替代。
- 分页不完整、登录页、HTML 错误页、空 JSON、未知状态、错误日期/节次、跨学期详情均不会发布坏快照。
- 单双周、跳周、多时段、合班、同课程名不同教学班、日期跨年、周次与星期相互校验。
- 当前 17 条记录可制作脱敏回归样本：11 条调课含 2 条仅换教室、6 条停课；采集时 2 条已通过、15 条待审。
- 这些样本在“仅正式事实”与“预测投影”统计中分开：不能把旧独立 HTML 的“全部通过”90 次/180 学时作为待审状态下正式课表总量。

### 12.2 稳定课次与数据保护

- 跨越多堂课改期，原 session ID、order_index、标题、内容、主材料、多材料绑定、进度、任务与签到均保持原对应关系。
- 取消第一堂/中间一堂/末尾一堂，仅取消精确匹配的 session；其余不换号、不移内容。
- 已通过且当前课表已体现的记录重复同步十次，不新增课、不重复应用、不改变 session ID。
- 模板自动生成、教师改写、AI 拆课、多个教学班共用课程、历史单班与合班均覆盖。
- 仅换教室、9/24 两堂同课程不同教室、10/11 同日四块安排、夜课 10—11 节作为具体场景。
- 现有 `tests/test_academic_sync_reconciliation_service.py` 的末尾取消用例必须补充中间取消和跨序移动，不能把原测试通过当作身份安全证据。

### 12.3 状态与并发

- pending→approved 且正式已生效：普通卡，预测撤下，session 精确迁移。
- pending→approved 但正式未生效：pending 样式和预测也撤下，正式原事实普通展示并告警，不搬课。
- pending→returned/rejected：撤预测，原正式课程正常；完整快照中的 missing 停止 active 预测并保留未知历史；缺页、接口失败不得进行 missing 判定或覆盖有效结果。
- 再次调课、同一原课多个待审目标、目标重复、正式与申请矛盾均可核对。
- 两个浏览器/worker 同时同步、旧响应迟到、提交后响应丢失重试、同步与人工排课/材料绑定并发，均幂等且不丢更改。
- SQLite 与原生 PostgreSQL 都测试；原生 PostgreSQL 验证真实行锁、唯一约束、事务回滚，不用 SQLite 模拟并发结论。

### 12.4 权限、只读与性能

- 教师跨账号、学生跨班、失效/停用学籍、撤销合班、篡改 session_id/semester_id 均被拒绝。
- 原/预测卡两端点击同一个正确 session，并继续访问该课材料/任务；不能只验证 URL 有参数。
- 学生 overview 保持只读，批量查询预算有上限；不因新增投影为每条课执行 SQL。
- 同步失败仍能浏览旧课表；未绑定课程可看真实信息，但不存在猜测的课次链接。

### 12.5 浏览器与全入口

- 教师首页、管理课表页、学生首页都使用同一个组件与相同状态合同。
- 桌面、窄屏、触屏、键盘、放大课表均验证 4px 透明间隙、虚线完整、原底色不变、预测使用混白实色底、深色文字清晰；悬浮放大时不得透出下方课次内容。
- 原/新标签双向跨周定位、高亮、筛选保留；仅换教室只一张卡；停课不造目标。
- 不发生点击标签误开课堂、点击课程误翻周、滚动详情误切周；原滚轮/拖动/放大功能回归。
- 静态资源版本一致，无新控制台错误；重新打开和刷新后使用服务器有效批次，不能依赖一次前端临时状态。

## 16. 调整指向线（2026-09-20）

- 放大周课表使用圆角实线箭头，从申请中的原时间指向拟调整时间。按明确的双向 `counterpart_event_key`、相同申请及已知课堂/课次身份配对，不按课程名、屏幕邻近位置或日期先后猜测；提前上课时箭头仍由原安排指向新安排。
