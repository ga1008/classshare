# 材料签名、批量操作与审批工作台改进计划

日期：2026-09-08。状态：设计方案，尚未实施。

本计划基于用户提供的界面截图与当前工作区代码。工作区已有正在进行的教务原生文档、审核意见和导出相关改动；本次仅新增这份计划，不改业务代码、数据库或线上环境。以下“现状”是本地代码核查结果，通知是否已在线上入库、邮件工作进程是否正常，仍需实施时只读核查。

## 1. 目标与覆盖范围

目标是让教师完成“选材料 → 配置每个位置的签名 → 提交申请 → 领导看实际材料审批 → 签名应用到材料 → 预览与打包下载”的完整流程，同时让领导能集中管理自己的待办。

第一轮完整接入当前已经注册签名点的三类文档：期末成绩登记表、试卷分析表、课程考核计划表。前两类共用教务双表列表，考核计划表另有列表与编辑器，必须分别适配。其他文档类型仅在已有导出能力和明确签名位置契约后接入，不凭文件后缀或标题猜测签名位置。

“同类文档”定义为相同具体文档类型、兼容的模板结构及相同签名点集合。`academic_final_material` 只是业务模块名，不能用它把成绩登记表和试卷分析表判为同类。教务同步的一组双表也不是一次签名申请的批次，两种批次必须区分。

## 2. 当前系统已具备什么，以及缺口在哪里

| 核查项 | 当前实现 | 对本次改进的影响 |
| --- | --- | --- |
| 共用签名组件 | `static/js/signature_point_workflow.js` 的 `SignaturePointControl`，由双表编辑器与考核计划表编辑器共用；搜索、身份按钮、原生 select、已选排序分开展示，申请浮窗又有一套候选操作 | 重构一个共享选择器，两处编辑器和批量浮窗统一使用 |
| 签名与特殊签名 | 已有 `personal` / `stamp`；可见的批语章对教师免申请，且不受默认职务过滤隐藏 | 沿用现有类型与权限，不新造与之平行的签章系统 |
| 标准批语 | 库内已有历史“同意”批语资源；当前原生试卷分析表另有“已核/同意”固定图片与意见文本默认逻辑 | 将标准批语统一呈现为可选特殊签名，解决重复显示、默认填入和清空语义 |
| 授权范围 | 既有授权绑定申请人、签名、材料、版本和功能点；同一版本可重复使用 | 批量只负责聚合，底层仍逐份、逐点、逐签名授权 |
| 审批规则 | 归属人或绑定本人任一同意即可；没有归属人和绑定本人时由超管审批；超管也可代批其他待审申请 | 保留规则；界面明确本人待办与管理员代批，不扩大普通领导权限 |
| 审批与应用 | 审批将授权置为可用，之后申请人还须选择签名并确认，才写入有序绑定 | 增加明确的自动应用意图，区分“已批准”和“已应用” |
| 版本 | 重新同步会更换 `signature_revision`；普通编辑以及重写教学分析经过的公共保存函数不更换它 | 现有“材料版本”不足以保证看到的内容与批准的内容一致；必须补内容版本契约 |
| 审批页 | 在“我的签名”底部；仅简单申请摘要；批量按钮前端仅对管理员显示 | 独立审批工作台，普通审批人也可批量处理自己有权审批的项目 |
| 审批筛选 | 列表 API 只有方向与状态，默认最多100条，服务内部最多500条；无完整分页和文档、申请人分类筛选 | 服务端分页、授权后筛选、数量汇总和申请人身份维度同时补齐 |
| 通知 | `_notify()` 已写消息中心，“签名审批”类别已登记，也有超期提醒；链接仅跳旧页面锚点 | 不能判定站内通知完全不存在；应查入库、接收人、角标、已读状态和深链接 |
| 邮件 | `EMAIL_ELIGIBLE_CATEGORIES` 缺少 `signature_workflow`，因此现有邮件入队函数直接判定不需要发送 | 这是已确认的代码缺口；还要验证发件配置和队列运行，不能只加白名单 |
| 材料列表 | 双表卡片无文档选择状态、无右侧文档属性栏；“可提交/待补全”都使用 `sync_status=completed` 对应绿色样式 | 独立计算完整性状态，增加选择模型与上下文操作区 |
| 导出 | 单文件走真实导出产物和共享渲染器；现有课堂材料 ZIP 打包的是存储树里的源文件/解析包 | 最终文档打包要调用当前导出契约，不能直接把课堂材料 ZIP 当成签名后文档包 |

当前主要关系：

```mermaid

    B --> E[真实 Word 等导出产物]
    E --> V[共享渲染器预览与下载]
    R --> N[消息中心]
    A --> N
```

| 9. 看实际文件后单个/批量审批 | 申请详情展示申请时冻结的真实文档，单文件或勾选多文件处理 | 预览与冻结 DOCX/PDF 对应；内容变更后不能误批新版本 |

| 11. 必要补充 | 自动应用、内容版本、幂等、失败重试、历史兼容、异步打包 | 从申请到签名后的正式文件完整回归 |

## 4. 必须先确定的业务规则

### 4.1 区分三个状态维度

- 材料生成状态：未生成、处理中、生成失败、已生成。
- 材料完整性：可提交、待补充；缺项由各文档类型的统一检查器返回。
- 签名流程状态：待审批、部分处理、已批准、已拒绝、已取消、材料已变更；另有应用状态“待应用、应用中、已应用、应用失败”。

审批通过不直接等于材料完整，材料生成完成也不直接等于可提交。列表、属性栏、审批详情、单文件导出与 ZIP 预检使用同一完整性结果，不在各前端复制判断公式。

建议返回 `can_submit`、`missing_fields`、`missing_signatures`、`warnings`、`blocking_errors` 及能力集合。批语可选这一新要求也应纳入完整性检查，不能保留“没有标准批语就必定不完整”的隐式规则。

### 4.2 个人签名与特殊签名

| 种类 | 授权 | 选择及排版 | 是否代表有人审批 |
| --- | --- | --- | --- |
| 本人或本人归属的个人签名 | 沿用当前直接使用规则 | 按确认顺序进入个人签字区 | 记录实际使用人，不虚构第三方审批 |
| 其他个人签名 | 仍须该文档该位置的有效授权 | 已获授权可直接应用，否则提交申请 | 有独立审批与使用记录 |
| 已核、同意等特殊签名 | 按现有可见范围直接使用 | 同一选择器内可选；审核栏的批语放意见区，姓名签名放签字区 | 不代表领导批准，不生成个人授权 |

新材料默认不自动填入“已核/同意”。这两种批语可不选；不选本身不使材料变成待补充。现有真实个人签名必填规则保留。批语不能替代缺失的个人签名；只有特殊签名、准备线下签字的材料可以经提醒下载，但仍按真实缺项标记。

保留自定义审核意见及明确清空能力。“无批语 / 特殊签名 / 自定义意见”是同一个意见槽的清晰选择，避免旧的文本优先级把已选特殊签名悄悄遮住。新配置默认每个意见槽一个标准批语；历史多图片批语原样可读，不批量重写。需要切换时由用户明确选择替换方式。

签名点注册信息增加允许的签名种类及排版槽：教师签字处通常只接受个人签名，审核意见栏可配置个人签名和批语。这个限制由后端执行，身份过滤仍只是方便挑选，不能越过签名可见范围。

### 4.3 排序表示排版顺序

多人签名的顺序用于最终文档排版，不隐含“先甲批准才能轮到乙”的串行审批。继续按现有规则并行申请，各位置独立审批。批语与个人签名在模板规定区域内分别排版，预览清楚显示两者位置。

保留每个签名点最多12项的现有上限。若某模板容纳不了该数量，提前给出具体排版限制；禁止无提示裁切、挤出表格或随意改变原表结构。

### 4.4 审批后如何真正落到文档

在提交前展示并默认勾选“该位置所选签名全部获批后，按当前顺序自动应用到这些文档”。申请人可以取消，改为获批后手动应用。这是新流程的明确使用意图；不替历史申请补造此意图。

- 一个位置全部所需授权满足后，原子应用该位置完整的有序选择。
- 部分人已批准时显示“已授权 X/Y，等待其余审批”，不静默省略未批准的签名，也不自动重排。
- 两个位置独立推进；系部位置完成无需等待院长位置，整份材料是否可提交另行判断。
- 某人拒绝但另一合法审批人仍可处理时，按既有任一同意规则继续待审，界面说明原因。
- 一个位置最终被拒绝，保留已获授权的历史；申请人可调整方案重新提交，系统复用仍有效的授权。
- 待审期间修改同一位置的签名组合、批语或顺序，需要更新该位置方案版本并明确替换旧方案，旧自动应用任务随之失效，不能覆盖新选择。
- 默认保留各文档现有绑定并追加新选签名，已有签名去重。需要“统一替换为此顺序”时，在提交摘要逐份显示被移除和新增的项目，不能默认抹掉已有签名。

## 5. 界面设计

### 5.1 统一签名多选下拉

每个签名位置只保留一个选择入口。收起时展示带序号的紧凑标签和状态，超过两行显示“另有 N 项”。已应用与待提交用状态区分，不把草稿选择显示为已生效。

展开后全部操作在一个弹出面板内完成：

1. 固定顶部：姓名搜索框；紧邻的“本岗位 / 全部可见”身份切换；必要时展开“可直接使用 / 需申请”筛选。
2. 中间列表：多选项按“个人签名”“特殊签名 · 无需申请”分组；显示姓名、职务、组织、授权状态与选中序号。特殊签名显示小型字样预览。
3. 同一面板内提供“候选 / 已选 N”切换；已选页支持拖动和上下移动，不额外展开另一列。
4. 固定底部：已选数量、清空本次选择与关闭下拉。正式保存/申请由宿主浮窗一个主按钮完成，避免两个不同的确认产生歧义。

初始尺寸建议：跟随输入框宽度，桌面常用360–480px；候选滚动区约280–360px，整个浮层不超过 `min(440px, 60dvh)`，通常显示6–8项。临近屏幕底部自动向上展开，不遮住主操作。窄屏横向距视口至少12px，必要时使用底部弹层；不把整张材料编辑器撑高。

交互要求：中文输入法组合期间不重建输入框；搜索防抖约200ms；切换筛选不丢失已选项、顺序、申请说明或滚动位置；键盘支持方向键、空格选择、Escape 关闭及焦点返回；触屏保留上下移动操作。实现 combobox/listbox 的多选语义，排序按钮使用合适的独立语义，不塞进不可交互的 option 结构。

单文档编辑器、单点申请和多文档申请共用同一选择数据模型。直接可用与需要申请的签名可以同时配置，由后端按各文档的实际授权状态拆分，不让用户来回切换两套候选列表。

### 5.2 材料卡片与右侧属性栏

宽屏采用“现有左导航 + 文档网格 + 约300–340px右侧属性栏”。右栏随视口固定在可视范围，其内部可滚动；窄屏改为底部选中操作条和可展开抽屉。

| 选择状态 | 属性内容 | 操作 |
| --- | --- | --- |
| 未选中 | 当前类型、筛选范围、文档数量、可提交/待补充统计 | 选择当前筛选全部、打包下载全部 |
| 单选 | 文档名、类型、课程、班级、学期、归属教师、更新时间、缺项、各签名点进度 | 现有编辑/预览/下载、申请或配置签名、打包所选 |
| 多选同类 | 共有属性；不同取值显示“多个值”及可展开分布；X份可提交/Y份待补充 | 批量申请签名、打包所选、清除选择 |
| 多选异类或模板不兼容 | 类型分布、共有属性、具体不兼容原因 | 打包所选；按类型分组选取后申请签名 |

初期共有属性以展示为主；只对已有安全批量修改契约的属性开放编辑。可见但无编辑权限的公开考核计划表可以按现有权限预览下载，不能因此申请修改其签名。按钮能力取所选文档权限的交集，并说明哪份材料限制了操作。

卡片空白点击切换选择，使用2px高亮描边、浅色背景与勾选标记，不改变卡片尺寸。按钮、链接、输入框、label、菜单、文本拖选、拖动和滚动优先走原行为。每卡提供明确的可聚焦选择控件，避免把含有多个按钮的整张卡片包装为嵌套按钮。

选择状态用稳定的“业务类型 + 实际记录ID”保存，不使用列表下标或课堂双表批次ID。轮询和重渲染保留选择；筛选暂时隐藏的选择保留，并显示“已选8份，其中2份不在当前筛选”，支持清除隐藏选择。记录删除或权限丢失时移除失效选择并提示。

状态标签统一文案“待补充”。可提交绿色配勾号，待补充琥珀色配提示图标，生成中蓝紫色，失败红色。右栏同时区分“内容缺项”和“待签名”，避免教师不知道下一步该做什么。

### 5.3 批量配置浮窗

使用一个浮窗，不为每份文档套一个嵌套浮窗。结构为：顶部已选文档摘要；主体按签名位置纵向分区；底部申请说明、自动应用选项及提交摘要。试卷分析表显示“系（教研室）审核”“教学院长审核”两个分区，各自一个统一选择器。

界面按“位置”配置，按“文档”展开查看差异。已完全相同显示当前值，存在差异显示“各文档当前配置不同”，未操作的位置默认保持原样。提供“保留原签名并追加 / 统一替换”模式，提交前显示每份的最终组合。

提交摘要例如：“3份试卷分析表；配置2个位置；需发起6项签名授权；2个审批账号收到待办；已有有效授权自动复用；特殊签名无需申请”。份数、位置数、个人签名数和审批人数分别计算，不混用。

预检找出已有进行中申请、内容版本变更、图片缺失、不可见签名或模板不兼容项。已有相同申请直接展示进度；冲突方案明确列出文档并允许用户返回修改或明确排除。禁止悄悄跳过后仍提示“全部提交成功”。

### 5.4 独立“签名审批与使用”页面

菜单建议路径 `/manage/me/signature-workflows`，与“我的签名”相邻。菜单职责：签名库管理图片、归属和范围；新页面处理申请、审批及应用记录。教师先完整接入；学生既有签名申请入口保持可达，并使用同一权限与通知契约，不误导学生跳到仅教师可访问的页面。

顶部四个页签：“待我审批”“我发起的”“我已处理”“使用记录”。认领申请在独立类型视图内处理，不与文档使用申请混合批量批准。

默认审批主工作区采用“申请列表 + 大幅文档预览”。列表按发起批次可折叠，每一行是一份材料；展示申请人、院系、文档类型、课程班级、申请时间、本人的待审位置和状态。预览占主要宽度，审批说明和按钮放预览上方或底部固定区，不再铺出第三、第四列。

点击文档立即展示被冻结的实际材料，支持页码、缩放、拖动和整页查看。文档外显示申请位置、签名顺序、批语及申请说明；需要定位时使用预览层标记和模板提供的位置元数据，不往原文档插入临时说明。待批准签名显示为拟使用信息，不能预先把未经授权的真实签名合入可下载文件。

主操作为“批准此文件中待我审批的签名”“拒绝”，批量工具条提供“批准选中 N 份”。若同一文件还有其他人负责的签名，必须明确“本次仅处理你有权审批的 X 项”。普通审批人享有批量能力，服务端对每项复核权限。管理员代批有清晰标识与本人审计记录。

批量操作前显示选中文档、本人处理项数、已查看数量和无法处理项目。无需强迫领导逐页点击，但每份文件都可以实际查看；不能只渲染第一份再误称全部已经检查。拒绝提供简短常用原因和补充说明，便于教师修订。

筛选采用一行搜索、常用筛选和可展开高级条件：

- 文档类型、申请类型（材料使用/认领/历史功能点授权）、本人处理状态。
- 申请人姓名；账号类别（教师/学生）与职务身份分开；职务来源复用账号有效任职。
- 学校、学院、系部；课程、学期、申请时间、超期未审。
- 普通审批人仅在自己的合法待办集合中筛选；超管才有平台管理视图。

默认按待办时间排序，保留当前筛选与页码，操作后聚焦下一份。菜单待办数来自工作流权限查询，消息已读数来自消息中心；读过消息不等于处理了待办。

## 6. 文档快照、版本与审批权限

### 6.1 申请时冻结真实文件

创建申请时保存材料当前规范化内容、模板标识/版本、内容哈希、材料版本及真实导出文件引用。快照至少持久保存当时的 DOCX/XLSX 原件；用于审批的 PDF 生成后也保存引用与哈希，以便后续版式审计。共享渲染器继续负责转换、页图和预览交互。

共享渲染器当前缓存默认24小时清理，不能把渲染缓存键作为唯一审批证据。快照进入受控的持久存储，通过哈希去重；多个签名位置和审批人复用同一文档快照。快照详情接口不携带文件字节或绝对存储路径。

准备快照的流程分两段：短事务读取内容与版本 → 在事务外生成真实文件 → 短事务复核版本并保存快照/申请。内容已变更则返回冲突，不把旧快照挂到新版本。批量准备可以显示进度；某份生成失败不得给该份发出“等待审批”的通知。

### 6.2 内容变更与签名变更分开

复用并完善 `signature_revision` 作为签名所针对的内容版本，增加规范化内容指纹；不要直接把 `updated_at` 当业务版本。

| 变化 | 处理 |
| --- | --- |
| 成绩、分析正文、课程班级、考试属性、申请人自定义审核文字、模板结构发生变化 | 产生新内容版本，旧授权不适用于新内容；待审申请标记材料已变更，并停止自动应用 |
| 按已确认方案新增获批签名、重试同一绑定、生成页图 | 不改变内容版本；更新签名/导出产物版本 |
| 更改同一位置的拟使用签名、批语或顺序 | 产生新位置方案版本，旧异步任务不能覆盖；变更已审批的展示方案须再次明确确认，不悄悄套用 |
| 仅列表排序、标签、界面折叠等未进入正式材料的属性变化 | 不使文档授权失效 |
| 重新同步、AI改写、重新导入或重建正式内容 | 均走同一个内容版本策略，不能仅个别入口换版本 |

第一次给旧材料建立内容指纹不批量撤销其既有授权。此后所有会改变审批对象的写入口必须接入统一策略。已经选用的本人签名和特殊签名可以按新版本重新校验并显式保留；他人旧版本授权不自动迁移。

还需记录申请时拟用签名图片的哈希：审批期间图片被替换、签名停用、可见范围或归属变化，提交审批及自动应用都重新校验，避免“批准A图片，最后应用B图片”。

### 6.3 审批专用访问入口

新增以申请ID定位的详情和预览接口。服务端校验申请人、该申请合法审批人或有审计权限的管理员，只授予关联快照的访问，不能为了让领导看材料而公开课程目录或放宽普通材料接口。

复用 `document_render_service.render_artifact()`、`render_preview_html()` 和当前用户绑定的渲染令牌。审批场景的页图/下载入口增加申请或快照权限复核，不能仅依赖旧令牌在数小时内一直有效。保留其他预览消费者的原接口契约。

审批动作携带预期材料版本、快照ID和位置方案版本。事务中再次核验实际版本、申请状态、审批身份、签名状态与图片指纹。材料发生变化时允许看旧快照和处理历史记录，但不批准其用于当前文档。

历史已处理事项的查看权限与留存跟随既有审计要求；待审权限和管理员角色发生变化后立即影响后续访问。单纯持有请求ID、同院系身份或曾经拥有列表页链接都不自动获得查看权。

## 7. 数据与服务设计

### 7.1 复用现有授权核心，新增少量聚合能力

保留 `signature_access_requests`、`signature_access_request_items`、`signature_access_request_reviewers`、`signature_point_flows`、`signature_point_flow_items`、`signature_point_bindings`、`signature_usage_logs` 的职责，不另建第二套审批表。

建议新增两个业务实体：

| 实体 | 主要信息 | 用途 |
| --- | --- | --- |
| `signature_application_batches` | 发起人、具体类型、请求幂等键、配置摘要、处理进度、时间 | 表达教师这一次对多文档的操作；用于列表分组、通知聚合与逐项结果 |
| `signature_material_snapshots` | 业务类型、真实记录ID、内容版本、内容指纹、模板版本、持久产物引用和哈希、文档标题/组织快照 | 为审批提供可追溯的真实文档，复用已有文件存储 |

扩展 `signature_point_flows`：申请批次、快照引用、方案版本、基准绑定版本、自动/手动应用、应用状态、错误摘要及应用时间。审批状态与应用状态独立，不能用“approved”同时表示文件已经生成。

扩展 `signature_point_flow_items`：支持直接使用与需审批项同存；沿用可空的 `request_id`，记录种类、授权方式、顺序及签名图片指纹。纯本人签名/特殊签名的方案不创建授权申请，但保留实际应用审计。

申请关联快照与申请人当时的学校、学院、系部和职务类别快照。组织快照用于解释历史与筛选，不能替代当前权限判断。账号可能兼任多职，筛选应按集合匹配。

新增索引围绕发起人+状态+时间、审批人+状态、文档类型、组织筛选、批次及材料版本设计。保留活跃申请/流程唯一约束，SQLite与PostgreSQL均需迁移及幂等验证。用实际列表查询计划确定复合索引顺序，不为所有筛选组合机械建索引。

### 7.2 把业务适配从路由中抽出

- 材料适配服务：由白名单映射具体类型到读权限、写权限、签名位置、内容指纹、完整性检查、真实导出和绑定持久化操作。先实现三类文档适配器，不做动态插件框架。
- 签名批量编排服务：预检、方案合并、按文档/位置创建流程、收集结果与提交后续应用任务；继续调用既有单项授权、审批和绑定能力。
- 文档打包服务：读取冻结导出计划，调用适配器生成文件，落盘压缩、报告错误并清理临时文件。
- 现有单文档保存与新批量应用共享持久化能力，同时更新规范化载荷、解析派生信息和当前绑定。不能只改绑定表导致列表、编辑器、预览各读一套状态。

### 7.3 建议接口契约

以下为拟定接口，实施时按现有路由前缀调整；使用结构化模型校验请求。

| 接口 | 职责 |
| --- | --- |
| `POST /api/material-signatures/selection-context` | 返回选中文档的共有属性、能力交集、完整性与兼容签名点 |
| `POST /api/material-signatures/preflight` | 按文档和位置校验最终组合，返回复用授权、需申请项、差异和冲突 |
| `POST /api/material-signatures/batches` | 幂等创建批次，返回逐文档结果或准备快照任务ID |
| `GET /api/material-signatures/batches/{id}` | 批次准备、审批、应用进度及每份结果 |
| `POST /api/material-signatures/batches/{id}/apply` | 显式应用已获批方案或只重试失败项 |
| 扩展 `GET /api/signatures/requests` | 受权分页、搜索、文档/申请类型、申请人/组织/时间筛选 |
| `GET /api/signatures/requests/{id}` 与 `/preview` | 有权限的申请详情、冻结材料预览 |
| 扩展现有单项/批量审批接口 | 版本与快照校验，普通审批人可处理自己的项目，逐项返回结果 |
| `POST /api/material-exports/preflight` | 明确所选/筛选范围、格式、缺项、阻塞错误与预检令牌 |
| `POST /api/material-exports/bundles` | 根据已确认预检计划创建持久化打包作业 |
| `GET /api/material-exports/bundles/{id}` 与 `/download` | 进度、文件清单、错误与有权限的最终下载 |

签名预检应按材料精确计算授权，不能取某一份的“已授权”结果应用到整批。候选查询也要服务端搜索与分页，修复现有仅读取最多500个候选后本地搜索导致后续签名搜不到的问题；已选项通过ID补取，并再次检查可见范围。

## 8. 通知与邮件闭环

扩展既有消息中心类别和 outbox，不再引入独立邮件发送逻辑。

| 事件 | 接收人 | 提示内容 |
| --- | --- | --- |
| 实际申请已创建、快照可用 | 合法审批人 | 谁提交了几份什么材料、哪些位置待审批，直达对应列表或文档 |
| 一份或一批审批完成 | 申请人 | 已通过/拒绝的项目，剩余项，是否正在应用 |
| 自动应用完成或失败 | 申请人 | 哪些文档已经更新，哪些需要重试或重新确认 |
| 内容已变更/申请撤回 | 相关待办参与者 | 旧待办状态变化和后续动作，撤销过期操作按钮 |
| 超期未审 | 当前仍需处理的审批人 | 复用既有48小时提醒、7天升级规则，不创建另一套定时器 |

同一批次对同一收件人的申请提醒聚合，避免“文档数×签名数”封邮件；批次之外的独立申请不错误合并。通知幂等键包含事件类型、批次或文档、版本和收件人。申请/审批事务同时写业务事件及消息/任务，失败回滚不留下幽灵待办。

落实 `signature_workflow` 的邮件白名单、重要级别默认值、专用动作文案和直达链接。当前实现给教师发邮件时优先使用收件教师自己的发件配置，此规则未必适合审批通知：签名审批场景建议优先使用已配置的平台通知发件账号，其次仅使用明确允许此用途的发起教师发件配置；收件人无需配置SMTP。实施时核查平台是否已有合适的配置入口，有则复用，没有则在系统设置中补显式配置，不借用任意教师凭据。

站内通知不依赖邮箱配置。邮件单独显示“排队中 / 已发送 / 未配置发件人 / 未配置收件邮箱 / 失败可重试”；SMTP成功不声称已进入收件箱。前端成功提示改为“申请已提交，通知已创建”，不无条件声称“审批人已收到通知”。

旧 `/manage/me/signatures#signature-requests` 入口和既有邮件链接继续可达：旧页保留短入口提示；前端识别旧锚点后定位新页。新链接精确带申请/批次ID，登录后可继续定位，已处理或已变更也能看到解释。

实际验证链：创建一条受控测试申请 → 核对接收人和消息入库 → 验证消息中心与菜单角标 → 验证邮件进入outbox → 运行受控投递检查 → 用收件账号打开链接 → 审批后申请人看到结果。测试阶段仅使用明确指定的测试接收账号，不发送给真实领导。

## 9. 打包下载的明确行为

右栏提供“打包所选 N 份”和“打包全部（当前筛选 N 份）”。“全部”由服务端按完整筛选条件解析，包括未加载分页；显示学期/类型/课程范围，不能只打包浏览器当前几张卡片。需要跨学期全部时先清除筛选，避免一次点击下载超出用户当前范围。

默认打包Word，提供PDF或Word+PDF格式选项；各文档沿用已有格式能力，未来表格文档按其原生格式处理。每份只导出一次；重复名称加班级、学期或稳定后缀，保留中文ZIP文件名并安全清理路径字符。

下载前服务端预检：

1. 冻结所选文档清单、当前内容/签名产物版本及格式，重新检查访问权限。
2. 区分可提醒继续的“不完整”与不可导出的阻塞错误。
3. 有不完整项时显示：“《动态Web程序设计·软工2402班·试卷分析表》、《……》内容待补充，是否继续打包下载？”可以展开逐份缺项。
4. 按钮为“继续打包下载”和“取消”。继续携带绑定用户、清单、版本和格式的短期预检令牌，不能靠一个宽泛布尔参数跳过全部检查。
5. 开始打包前版本已变化则重新预检；不能把用户确认的旧缺项清单默默套给新文件。

允许继续的情形：缺少审核签名、可填写字段等但仍能忠实导出当前文档。继续后确实将这些文档纳入包内，保留空缺，不伪造意见或签名，不把状态改为可提交。包内增加简明“材料清单.txt”，列出文件名及待补充说明；不擅自修改正式模板或盖水印。

不能被“继续”绕过的情形：无权访问、材料不存在、原始模板损坏/缺失、文件生成失败，或内容超出教务原生模板允许的空间。预检明确列出，可由用户排除后重试；运行时个别失败则任务标为部分成功，列出成功/失败文件并提供重试，不能把缺文件的ZIP说成全部成功。全部失败不生成空包。

预检清单与作业进度持久保存；关闭页面不丢任务。压缩在临时文件中流式写入，不把所有DOCX、PDF和ZIP同时堆内存；下载鉴权，过期清理，失败清理，下载任务不触发新的签名使用授权或重复使用通知。

## 10. 并发、性能及一致性

- 授权最小单位继续是“申请人 + 签名 + 文档 + 内容版本 + 位置”，批次不产生跨文档通用授权。
- 批量提交使用请求幂等键；重复点击/网络重试返回同一结果，不重复申请、通知或任务。仍保留数据库活跃流程唯一约束。
- 原子边界为单文档的本次配置；一份的多个位置要么一起建好，要么完整回滚。不同文档可分别成功，明确逐项结果。统一按材料ID和位置键排序加锁，避免批量锁顺序反转。
- 同一位置替换绑定继续使用事务锁，并加入基准绑定/方案版本校验。审批、撤回、编辑和后台自动应用争用时只能有一种合法结果。
- 当前批量审批虽捕获业务异常，但没有逐项保存点；改为每项/每份显式事务隔离。不能将失败项的前半段写入留到外层提交。
- 审批状态变更和创建应用作业在同一事务内；后台作业按文档/位置幂等应用，记录申请人使用意图和实际执行主体，不能把领导记为文档申请人。
- 自动应用前复核内容版本、方案版本、图片指纹、授权、归属和当前可见范围。已有新编辑则停止并提示，不覆盖。
- 渲染、PDF转换、压缩都在事务外、HTTP主线程外执行。复用持久化作业的claim/lease/retry能力，注册独立文档任务类型与受限worker；不把大文件渲染放入统一提醒调度器，阻塞邮件和其他定时任务。
- 保留共享渲染器的内容哈希缓存、逐页懒加载、单key锁与并发上限。其信号量目前是进程内的，多worker场景需专用渲染worker或跨进程限额，不能误以为每进程并发1就等于服务器总并发1。
- 列表、共有属性和审批摘要批量查询；不按“文档×位置×候选”逐个请求。详情展开才加载页图，列表不提前渲染全批PDF。
- 建议首轮批量提交上限50份，审批底层每次最多50条沿用现状；文件与授权条数分别计数，超过底层数量时由编排任务分块。压测后调整上限，不以浏览器一次发出数百请求实现批量。
- 预览生成失败与绑定失败分开显示：绑定成功但预览失败可重试渲染，不重复审批；绑定失败则不能显示“已应用”。

## 11. 历史数据和既有功能保护

1. 迁移只增加必要表列和索引；旧字段、签名ID、顺序、归属、授权记录与下载文件保持可追溯。
2. 保留旧标量签名ID到多选列表的兼容读取，不批量重写历史材料内容。
3. 标准批语资源以稳定业务键和内容哈希幂等入库；旧“同意”资源仍可读，新材料可选择正确的“已核/同意”资源，不重复播种。
4. 历史材料已保存的意见、明确清空及批语图不自动改变。新材料采用“可选”规则，旧材料打开不会凭空增加批语。
5. 历史申请没有申请时快照，不能事后把当前文件冒充原快照。待审且有材料的申请由申请人确认当前版本后补齐审阅材料；没有具体材料的旧功能点申请转到明确的历史类型，引导选择材料重新提交。已批历史授权按原契约读取，不虚构已查看记录，不自动给历史待审申请套用自动应用。
6. 原编辑、生成、导入、重新同步、个人签名上传/认领/归并/解绑、学生签名入口和单文件下载保持原能力。需要调整的旧申请入口提供新材料选择路径，不能留下直接授予无文档新授权的旁路。
7. 原生教务表的固定表格、字体、签字/意见分区和预览导出一致性作为回归重点，不能为新UI改坏正式文档。
8. 说明使用现有 `ui_explanation`；真实错误、内容变更、待补充和处理结果保持可见，不藏进说明浮窗。
9. 当前工作区与本需求相关文件存在其他改动；实施前复核最新版本和差异，在稳定基线上衔接，不回退或覆盖其他任务成果。

## 12. 实施顺序与阶段交付

| 阶段 | 工作 | 交付与通过条件 |
| --- | --- | --- |
| A. 基线与业务契约 | 确认三类文档适配点、数据关系、签名及批语规则；只读追踪站内通知；整理现有回归基线 | 一份契约和测试场景清单，明确线上待验证项；稳定相关工作区改动 |
| B. 一致性底座 | 完整性检查器、内容版本策略、快照持久化、审批专用权限、字段/索引迁移、批量幂等与事务隔离 | 单份“真实文档快照→审批→有序绑定→导出”完整通过；两种数据库迁移可重复 |
| C. 单点交互与特殊签名 | 重构共享多选下拉，统一本人/已授权/需申请/特殊签名；接入双表和考核计划表编辑器 | 中文输入、排序、清空、旧数据、移动端和原表版式验证通过 |
| D. 材料列表与批量申请 | 稳定选择模型、状态区分、右侧属性栏、共有属性、批量配置及自动应用 | 单选/多选、相同/不同模板、已有签名差异、部分失败和重试闭环 |
| E. 审批工作台与通知 | 新菜单、文件列表与真实预览、筛选分页、单份/批量审批、深链接、角标、邮件与聚合通知 | 普通领导和管理员权限测试；申请人收到结果；关闭页面后应用仍完成 |
| F. 最终文档打包 | 已选/筛选全部、预检提示、异步导出ZIP、格式选择、逐份清单与失败恢复 | 所选含待补充文件能继续下载；包内数量、内容、签名与预览一致 |
| G. 集成验收与发布准备 | 权限、并发、浏览器、原生文档、迁移演练、负载与回滚检查 | 业务验收矩阵全部通过，交付发布清单与核验结果 |

阶段B必须先于实际上线的新批量审批；不能先开放“批量批准”，后补文档快照和版本核验。C的交互样式可以与B的后端工作并行，但以同一接口契约集成。

发布准备包含隔离数据库迁移演练、旧/新入口兼容和开关回退。实际部署、生产通知发送和Git提交推送不属于本轮计划编写，待实施任务按授权执行；回退优先关闭新入口和自动应用任务，保留审计数据，不删除新增业务记录。

## 13. 验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 输入中文姓名，连续切换身份过滤 | 不打断输入法、不丢说明与已选项，可找出分页后的签名 |
| 同一点选A、B再改为B、A | 草稿状态明确，确认后的实际DOCX顺序为B、A |
| 只选“已核/同意” | 无授权申请；可移除；个人签字区不出现批语；不冒充领导已审批 |
| 不选标准批语，但其他必需内容与个人签名齐全 | 按新的可选规则可提交，不被旧默认意见判定阻止 |
| 三份试卷分析表分别申请系部A与院长B | 每份每处权限独立；A审批不授予B，也不授予第四份材料 |
| 已有不同签名的多份文档 | 默认保留；统一替换必须在提交摘要看到具体差异 |
| 成绩登记表与试卷分析表混选 | 可查看共同属性和打包，不作为同类位置一键申请 |
| 点击卡片内预览、下载、编辑，或拖选文字 | 原动作有效，不误切换选择 |
| 刷新列表、切换筛选、轮询任务 | 稳定保留选中，隐藏选择数量可见，过期选择可解释 |
| 普通领导批量审批 | 只能处理本人有权审批项；同院系非审批人不可看申请快照 |
| 同一申请的归属人与签名者同时审批 | 按现有任一同意规则产生唯一合法终态，通知/使用不重复 |
| 领导打开预览后教师改正文或AI重写 | 旧快照仍可解释，不能对新内容使用旧批准；停止旧自动应用 |
| 一个位置审批应用完成，另一个位置随后审批 | 内容版本不因正常签名应用变化，两处可先后成功 |
| 审批期间签名图片替换、范围收窄或账号失权 | 再审批/应用时拦截并解释，无旧令牌越权 |
| 打包选中含2份待补充材料，点击继续 | 提示列出名称和缺项；ZIP含这些文件；未伪造补齐 |
| 同一提示点击取消 | 不创建打包作业，不改变材料和选中状态 |
| 包含模板错误或越权材料 | 不用“继续”绕过，明确失败或排除后的清单 |
| 导出时发生并发编辑 | 导出冻结的确认版本或重新预检，不同文件不混用随机版本 |
| 批量10份中1份失败 | 其余有明确结果，失败项不半写；只重试失败项不重复申请 |
| 页面关闭、网络重试或worker重启 | 作业可恢复、幂等，不依赖前端轮询完成实际绑定 |
| 预览缓存过期 | 从持久快照恢复预览，审批证据仍在 |
| 邮件未配置、队列失败、SMTP发送成功 | 分别显示真实状态，站内待办一直可用，不虚报送达 |
| 大批量PDF与并发用户 | 常规列表/保存不等待整批渲染，不突破服务器全局渲染额度 |
| 原生试卷分析表和成绩登记表 | 实际DOCX→PDF/页图检查，无表格变形、签名溢出或预览下载差异 |

优先扩展已有 `test_signature_point_service.py`、`test_signature_workflow_scope.py`、`test_signature_workflow_service.py`、`test_academic_review_opinions.py`、`test_document_render_service.py` 与对应浏览器测试。新增测试针对快照权限、版本竞争、批量事务、通知入队和ZIP内容等业务不变量，避免只断言DOM字符串或重复实现函数。

浏览器验收覆盖桌面、窄屏与触屏：浮层边界、焦点、中文输入、跨筛选多选、排序、双层dialog交互、签名状态刷新、申请详情及批量提示。文档验收必须检查实际产物和页面图，不以接口200或文件能打开替代。
