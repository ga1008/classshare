# 文档功能导入、生成、预览、导出 AI 实施指南

> 面向对象：后续参与 LanShare 文档功能开发的 AI 与工程师。
> 适用范围：教案、课程考核计划表、评分细则、试卷、教学大纲、教学日历、总结表、签名表等一切需要“导入解析 → 结合课堂/材料生成 → 编辑 → 预览 → 导出 Word/PDF/图片”的学校格式文档。
> 核心要求：不要只改一个模板函数或一个前端页面。文档功能是一条完整业务链，任何一环独立正确都不等于整体可用。

## 一句话原则

新增或修复一种文档类型时，必须同时理解并闭环这些层：

1. 数据库与结构化 schema
2. 导入解析与 AI 抽取
3. 课堂、课程、教材、教务同步数据的确定性预填
4. AI 生成提示词与后置校验
5. 编辑器字段、签名、提示与权限
6. 预览路由
7. DOCX/PDF/PNG 导出模板
8. 单元测试、渲染截图 QA、部署验证

如果预览和导出不是同一条渲染链路，未来几乎一定会出现“预览是新的，导出还是旧的”或“预览看起来对，下载完全不对”的问题。

## 必做的代码地图梳理

动手前先全仓搜索并画出真实链路。不要凭文件名猜。

```powershell
rg -n "document_type|template_key|export_payload|render_preview|export|import|generate|signature|assessment_items|lesson" classroom_app templates static tests docs
```

对每一种文档类型，至少定位这些位置：

| 层 | 必查内容 | 常见文件 |
| --- | --- | --- |
| 路由 | 导入、生成、内容保存、预览、导出接口 | `classroom_app/routers/*` |
| schema | 表结构、字段 JSON、状态字段、签名绑定 | `classroom_app/db/*` |
| service | normalize、CRUD、导出字段构建、权限 | `classroom_app/services/*_service.py` |
| import | 本地抽取、AI JSON schema、签名图片归集 | `*_import_service.py` |
| generation | 课堂上下文、提示词、fallback、进度 | `*_generation_service.py` |
| final material | `export_payload.fields/structured`、通用期末材料逻辑 | `material_final_document_service.py` |
| export template | DOCX/PDF/XLSX 版式、字体、表格、页脚 | `material_export_template_service.py` 或专用 docx service |
| editor | 字段控件、表格行、签名库、保存、预览刷新 | `static/js/*_editor.js`、`templates/*` |
| tests | 结构、字段、导出、坏例复现 | `tests/test_*` |

不要跳过已有共用服务。很多“重复劳动”和“互相冲突”来自新建一套孤立逻辑，而不是复用现有 normalize/export/import 约定。

## 正确的数据契约

文档类型必须有一个稳定的 canonical payload。建议遵守：

```json
{
  "fields": {
    "course_name": "",
    "class_name": "",
    "teacher_name": "",
    "academic_year": "",
    "semester": "",
    "date": ""
  },
  "structured": {
    "sections_or_rows": []
  },
  "notes": [],
  "warnings": []
}
```

期末材料类文档优先使用：

```json
{
  "template_key": "assessment_plan",
  "document_group": "final_material",
  "document_type": "assessment_plan",
  "fields": {},
  "structured": {}
}
```

### 字段分工

- `fields`：模板上看得见的元信息字段，例如课程名称、班级、教师、学年学期、日期、课程类别、学分学时、教材。
- `structured`：文档主体结构，例如教案课次、考核项目、评分细则条目、试卷大题。
- `notes`：模板固定说明，不要混入 `fields`。
- `warnings`：解析或生成风险提示，不要进入正式导出正文，除非模板本身要求展示。
- `queryable_fields`：给搜索、筛选、后续串联使用，不能替代导出字段。

### 严禁事项

- 严禁把文件路径、签名路径、图片 URL、数据库 ID、JSON 片段写进可见文档。
- 严禁让 AI 覆盖确定性字段，例如课程名、班级、任课教师、教务同步的课程类别、学分、学时。
- 严禁导入时“补全”源文档没有的值。导入是还原，不是创作。
- 严禁生成时只描述 JSON 格式却不说明业务含义。AI 会按字面拼装出看似合法但业务错误的内容。

## 导入解析指南

### 导入的目标

导入不是“生成一份更好的文档”，而是把已有 Word/PDF/图片尽量忠实地还原成系统结构化数据。

导入要做到：

- 原文有的字段尽量识别。
- 原文没有的字段不要编。
- 表格行顺序不变。
- 分值不偷偷改。
- 手写签名按图片处理。
- 解析不确定时进入 warnings 或 import_preview，让教师确认。

### 导入解析提示词必须写清字段来源

不要只写“请解析课程考核计划表”。要写：

- `course_name` 来自“课程名称”单元格。
- `class_name` 来自“专业年级班级”单元格，不得用课程名称、教学班号、文件名替代。
- `examiner_name` 来自“命题教师”的文字姓名。
- `reviewer_name` 来自“系（教研室）主任审核签字”处的文字姓名。
- 签名图片单独入库，不得当作文字字段。
- `assessment_items` 只来自“考核形式 / 考核技能/内容 / 分值”三列表。

教案导入也一样：

- 封面字段从封面取，不从正文猜。
- 课次从表格顺序取，不要合并丢失。
- 教学目标、重点、难点、方法、过程、旁批、后记要按原表位置映射。
- Mermaid 或流程图源文本不能当作 Word 可显示图，后续导出必须渲染成图片。

### 表格解析技巧

- 用表头语义判断，不要靠“第几个表格”。
- 表头可能有空格、换行、全角/半角差异，要 normalize。
- “分 值”“分值”“分　值”应归一。
- 表后注释不要被误认为表格内容。
- 如果表格跨页，按连续表头或列数合并，但不要把下一张无关表格接上。

### 签名解析技巧

- DOCX 中签名通常是 embedded image，不是文字。
- 同一文档可能有多个图片，需按所在单元格或附近标签判断 role：命题教师、系主任、主管领导等。
- 图片入库应 hash 去重。
- 入库后绑定到文档记录，不要把路径写进 `fields`。
- 如果无法判断签名属于谁，放入 import_preview 让用户选择，不要随机绑定。

### 导入踩坑

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 把说明文字解析成字段 | `course_name` 变成“课程名称必须与...” | 分离 notes 和 metadata 表 |
| 用文件名推断班级 | 班级错、格式错 | 优先模板单元格，其次教务/课堂数据 |
| 把签名路径写入姓名 | 导出出现 `/app/data/media/...png` | 姓名字段只放姓名，图片路径只给 export renderer |
| 导入时自动调分 | 原始资料被篡改 | 标记“不等于 100”，让教师核对 |
| 忽略页面图片 | 扫描件/手写签名丢失 | 文本 + 页面图一起给 vision 模型 |

## 根据课堂和材料生成指南

### 生成的目标

生成不是自由作文，而是基于课堂事实填充官方模板。AI 只能补“内容”，不能随意改“身份字段”。

确定性字段优先级：

1. 教务同步数据
2. 课堂/课程/班级数据库
3. 教师账号与组织归属
4. 已绑定教材与课程材料
5. 用户补充提示
6. AI 推断

AI 推断只能作为最后兜底，并且要进入 warnings。

### 课堂上下文必须包含

- 课程名称、课程代码
- 班级名称、行政班/教学班、专业、系部、是否专升本
- 任课教师、学院、系部
- 学年、学期
- 总学时、学分、课程类别
- 教务考核类型、考试方式、课程性质
- 教材标题、作者、出版社
- 课次列表：日期、周次、星期、节次、章节、材料
- 已绑定课程材料：标题、摘要、重点内容
- 邻近课次上下文，尤其是教案生成

### 生成提示词必须写业务边界

坏提示词：

> 生成 assessment_items，每项包含 assessment_form、content、score，合计 100。

好提示词：

> 这是期末考试/期末考核的命题计划表，不是课程成绩构成表。只写期末考试本身考什么、怎么考、多少分。不得写平时成绩、考勤、课堂表现、课后作业、阶段性实验、过程性成绩。通常 3-6 行，合计 100 分。

坏提示词会让 AI 生成“平时成绩 20 + 阶段项目 30 + 期末项目 50”这种业务上完全错误但 JSON 合法的结果。

### 生成后必须校验

每个高风险文档类型都要有后置校验器。

课程考核计划表示例：

- 行数是否 3-6。
- 分值是否合计 100。
- 是否出现平时、考勤、课堂表现、作业、阶段性、过程性等禁词。
- 是否只描述考试大类和技能/内容。

教案例子：

- 课次数是否等于 `class_offering_sessions`。
- 每次课的节数是否由总学时和课次数计算。
- 一小节是否 40 分钟。
- 总时间分配是否等于本次课节数 × 40。
- 是否包含知识目标、能力目标、素养目标、重点、难点。
- 流程图是否已渲染成图片。

### 生成 fallback

AI 不可靠时不能让用户拿到空文档。必须有本地 fallback：

- 用模板默认结构生成完整草稿。
- 用课堂字段填确定性元信息。
- 用教材/章节标题生成保守内容。
- 给 warnings：需要教师复核。

fallback 要可导出、可编辑、可保存，不是只返回错误。

## 导出和版式复刻指南

### 导出的目标

导出的 Word/PDF 是正式材料，不是网页美化稿。目标是尽量一比一复刻官方样表。

必须核对：

- 页面大小
- 上下左右边距
- 页眉页脚距离
- 字体和字号
- 标题位置
- 表格总宽度
- 每列宽度
- 每行高度
- 边框粗细
- 单元格合并
- 段前段后
- 行距
- 下划线长度
- 页脚或底部印制文字
- 图片大小与位置

### DOCX 实现技巧

- 用 `python-docx` 或 OOXML 控制，不要拼 HTML 期待 Word 自动转对。
- 表格必须 fixed layout，禁用 auto-fit。
- 明确设置 `w:tblGrid`、`w:gridCol`、`w:tcW`。
- 行高、边框、页边距转成 twips/EMU 常量。
- 中文字体要同时设置 ascii、hAnsi、eastAsia。
- 下划线不要靠普通空格。Word 可能不渲染尾部空格下划线。用 NBSP、tab stop 或底边框。
- 长文本换行要考虑缩进，尤其是教材超过三行时，续行要和正文左边对齐。
- 页底固定文字不要被正文推走，必要时使用页脚、绝对位置策略或限制正文区域高度。

### 预览必须同源

预览不是再写一套 HTML 表格。推荐：

1. 正式导出 DOCX。
2. 转 PDF。
3. iframe 或对象预览 PDF。
4. Word/PDF 下载也从同一套 export artifact 出。

如果为了性能保留 HTML 预览，也必须明确标记为“编辑预览”，并保留正式打印预览入口。学校正式文档默认应走 PDF 打印预览。

### Mermaid/流程图

Word 不能直接显示 Mermaid。

处理方式：

- 识别 Markdown/Mermaid code fence。
- 调用渲染工具生成 PNG/SVG。
- 将图片插入 DOCX。
- 导出前渲染验证图片非空。
- 不要把 Mermaid 源码直接放进 Word 正文，除非用户明确要源码。

## 签名库和签名导出指南

### 字段拆分

签名相关数据至少拆成：

- `examiner_name`：可见姓名
- `examiner_signature_id`：绑定签名 ID
- `examiner_signature_image_path`：仅导出 renderer 使用
- `reviewer_name`
- `reviewer_signature_id`
- `reviewer_signature_image_path`

不要把这些混成一个字段。

### 自动匹配

匹配签名时：

- 先精确匹配 subject_name/name。
- 再限制 school_code。
- 同系部、同学院优先。
- 用户无权限使用时不要强行插入。

### 缺失处理

如果必需签字人没有填写：

- 编辑器要提示“请填写姓名”。
- 导出字段可显示“【系主任未填写】”或业务约定提示。
- 用户填写姓名后可从签名库选。
- 签名库没有时允许上传，上传后自动入库并绑定。

### 图片尺寸

- 签名图片高度要保守，避免撑高行。
- 姓名和签名图片应同一单元格、合理间距。
- 不要另起多段导致单元格高度失控。

## 课堂和教务字段映射指南

### 班级字段

“专业年级班级”不是课程名，也不是教学班流水号。

优先级：

1. 行政班/教务班级名
2. academic_class_name
3. class.name
4. 多班合并显示

系别要缩写：

| 原始系/专业 | 显示 |
| --- | --- |
| 软件工程 | 软工 |
| 网络工程 | 网工 |
| 计算机科学与技术 | 计科 |
| 人工智能 | 人工 |
| 数据科学与大数据技术 | 大数据 |
| 数字媒体技术 | 数媒 |

如果班级是专升本，追加“（专升本）”。

错误例子：

- `动态 web 程序设计-0001`
- `服务器配置与管理`
- `专业`

正确例子：

- `软工 2406、2407、2408班（专升本）`
- `计科 2401班`

### 日期字段

不要默认用当天日期，除非没有更好的依据。

- 教案授课时间：来自 session 日期、周次、星期、节次。
- 考核计划命题日期：默认课程最后一次有效授课日，可让用户改。
- 取消课次不参与最后日期计算。
- 日期导出要按模板格式，而不是原始 ISO。

### 学年学期

- 从 semester 或教务同步中解析。
- 导出时按模板下划线片段渲染。
- 不要把 `2025-2026 2` 直接放一行。
- 注意有些模板只给年份后两位加下划线。

### 课程类别、学分、学时、教材

- 从教务同步信息取完整值，例如“专业限选课程”，不能简化成“专业”。
- 学分、学时要落在模板下划线中间。
- 教材长文本换行要和正文左边对齐。
- 教材不要因太长把底部印制文字顶到下一页。

## 具体文档类型注意事项

### 教案

- 封面必须按官方样式：校名/logo、标题、学年学期、课程信息、底部印制文字。
- 正文每次课一张表，授课时间要有下划线片段。
- “知识目标：”“能力目标：”“素养目标：”“重点：”“难点：”应加粗。
- 教学内容及过程必须明确时间安排。
- 一小节课是 40 分钟；课时数和课次数不一致时要换算。
- 例如 32 课时、16 次课，代表每次课 2 小节，即 80 分钟，过程安排要写清两节各 40 分钟。
- Mermaid/流程图必须渲染成图片插入。

### 课程考核计划表

- 这是期末考试/期末考核命题计划，不是成绩构成表。
- `assessment_items` 只写考试部分：考核形式、题目/技能/内容大类、分值。
- 通常 3-6 行。
- 严禁混入平时成绩、考勤、课堂表现、作业、阶段实验、过程考核、小组答辩。
- 命题教师姓名要粗体，签名图片紧跟姓名。
- 系主任姓名必须有输入/提示；可从签名库匹配或上传。
- 命题日期默认最后一次课日期。

### 评分细则

- 必须依赖对应试卷或考核计划，不要凭课程名泛泛写。
- 分值结构要和试卷/考核计划一致。
- 每一大题或任务要有扣分点、给分点、例外处理。
- 不要只写“按完成质量评分”这种不可执行描述。

### 试卷

- 优先继承考核计划分值分布。
- 题目必须可执行、可评分、可提交。
- 上机/项目类题目要写清文件名、截图、压缩包、提交要求。
- 导出模板负责标题、学年学期、学生信息、密封线、页脚时，AI 正文不要重复写这些。

## 测试和验收清单

每个文档类型至少补这些测试：

- normalizer：别名、缺字段、默认值、非法值。
- import：表格抽取、字段映射、notes 不误入字段。
- generation：坏 AI 输出过滤、fallback 完整性。
- export fields：签名路径不泄露、缺失签名提示。
- DOCX 结构：页边距、表格宽度、列宽、行高、页脚、关键标签。
- editor JS：语法检查，必要时加浏览器交互测试。

命令示例：

```powershell
python -m unittest tests.test_assessment_plan_service tests.test_final_material_assessment_plan
python -m py_compile classroom_app\services\xxx.py
node --check static\js\xxx_editor.js
git diff --check
```

## 新增一种文档类型的执行清单

按顺序做，不要跳步：

1. 找官方样表，渲染成 PDF/PNG。
2. 标注每个字段来源、类型、是否可编辑、是否来自教务。
3. 设计 canonical payload。
4. 写 normalizer。
5. 写导入 prompt 和 parser，明确字段来源。
6. 写课堂/材料 context builder 或复用已有 builder。
7. 写生成 prompt，强调业务边界。
8. 写生成后置 validator。
9. 写本地 fallback。
10. 写编辑器字段、表格、签名、提示。
11. 写导出模板，提取官方 OOXML 常量。
12. 让预览复用导出 PDF，而不是手写另一套 HTML。
13. 补单元测试。
14. 生成样例 DOCX。
15. 渲染 PDF/PNG 检查。
16. 对照用户截图逐项核对。
17. 再考虑部署和 git。

## AI 提示词模板

导入 prompt 应包含：

```text
你是文档解析助手。请忠实解析原文，不要补写、不改分值、不改顺序。
必须返回 JSON，不要 Markdown。
字段来源：
- course_name 来自“课程名称”单元格。
- class_name 来自“专业年级班级”单元格。
- ...
手写签名图片不要作为文字输出，系统会单独入库。
无法确定的字段留空，并在 warnings 说明。
```

生成 prompt 应包含：

```text
你是固定模板填表助手，不是自由写作助手。
确定性字段必须沿用系统给出的 fields，不得篡改。
请根据 classroom_context、教材、课程材料生成 structured 内容。
业务边界：
- 这是 XXX 文档，不是 YYY。
- 必须包含 A/B/C。
- 严禁出现 D/E/F。
输出必须是 JSON。
```

导出实现不靠 prompt，靠确定性代码和渲染验收。

## 最容易被 AI 忽略的红线

- 不要用“看起来差不多”的网页预览代替正式打印预览。
- 不要把导入和生成混为一谈。
- 不要让 AI 改教务同步字段。
- 不要漏掉签名库权限和签名图片处理。
- 不要把当前日期当作所有文档日期。
- 不要假设课程总课时等于课次数。
- 不要在 Word 中直接塞 Mermaid。
- 不要只写单元测试不渲染。
- 不要新增一条平行导出链路绕开已有模板服务。
- 不要为了赶进度复制一份相似 service，后续会互相冲突。

## 完成定义

只有同时满足以下条件，才能说一个文档功能完成：

- 导入能还原标准样表字段和主体结构。
- 生成能基于课堂、教材、材料产生业务正确内容。
- 编辑器能修改关键字段并处理签名/缺失项。
- 预览和导出同源。
- DOCX/PDF 渲染接近官方样式。
- 坏例有测试覆盖。
- 渲染截图已人工检查。
- 不污染其他文档类型。
- 不泄露路径、ID、调试文本、敏感数据。
