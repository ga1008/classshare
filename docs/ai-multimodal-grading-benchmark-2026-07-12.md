# 多模态学生作业评分模型实测报告（2026-07-12）

## 1. 执行结论

本次不是用公开图片或厂商样例做演示，而是从 LanShare 远程生产库中只读分层抽取了 20 份真实学生作业，在本地匿名编号后，以完全相同的题目、评分规则、附件预处理和输出协议，对 6 个已充值或已配置的模型进行了 240 次有效调用。评测同时覆盖评分、视觉字段识别、重复调用稳定性、延迟、Token 和按公开单价估算的成本。

建议不要把豆包整体替换成单一模型，而是改为分层路由：

1. **默认快速模型：`qwen3.6-flash`**。用于图片文字/界面元素识别、客观题辅助抽取和简单作业，速度明显领先，单次主评分估算约 0.0107 元。
2. **默认深度评分模型：`qwen3.7-plus`**。用于主观题、代码、长文本和多图作业。本次独立复核命中 3/4，质量/速度/成本最均衡，主评分成本比豆包 Pro 低约 89.4%。
3. **高风险兜底：保留 `doubao-seed-2.1-pro`**。只在证据冲突、模型分差超过 10 分、重要作业或教师复核前调用。本次独立复核 4/4 命中且最稳定，但成本和延迟显著最高，不适合全量常规评分。
4. **GLM 作为影子模型或第二意见，不直接作为唯一最终评分器**。`glm-4.6v` 与旧分数的 MAE 最小，但独立复核只命中 1/4，重复评分平均极差 13.75 分；`glm-4.6v-flash` 免费但长卷很慢，且同样存在过度给分和不稳定问题。

按本次实测的单次主评分成本，若采用“70% 千问 Flash + 20% 千问 Plus + 10% 豆包 Pro”的保守组合，估算平均成本约 **0.0348 元/份**，相对全量豆包 Pro 的 0.2253 元/份节省约 **84.6%**；若豆包 Pro 兜底率降至 5%，节省可接近 **89%**。这比直接换成最便宜模型更稳健。

## 2. 本次测试回答了什么

本次评测刻意把四类容易混淆的能力拆开：

- **历史分数一致性**：模型能否接近系统里已有的教师/历史评分。
- **独立评分正确性**：对源代码、长卷答案和跨附件证据重新审计后，模型分数是否落入合理区间。
- **视觉识别准确性**：能否正确识别网页截图、TCP 时序图中的客观字段。
- **工程可用性**：输出 JSON 是否稳定，速度是否适合交互，失败是否可恢复，成本是否可持续。

“接近历史分数”不等于“评分正确”。历史记录可能来自旧模型辅助、教师快速确认或不完整证据。本次在报告中将两者分列，避免用单一 MAE 得出错误结论。

## 3. 样本与公平性设计

### 3.1 分层样本

| 类型 | 数量 | 主要考察能力 |
|---|---:|---|
| 教师已落分的网页截图作业 | 8 | 页面元素、数量、空值、截图可用性及基于规则评分 |
| TCP 握手/挥手可视化图 | 4 | 流程阶段、序列号/确认号、状态迁移和细节完整性 |
| Python TCP 代码作业 | 3 | 多文件代码理解、需求覆盖、异常与循环逻辑 |
| 38 题长文本试卷 | 3 | 客观题、计算题、综合题和长上下文评分 |
| 11 图复杂网络实验 | 2 | 多图证据、计算值、抓包/连通性以及跨文件一致性 |
| **合计** | **20** | 覆盖轻量识别到深度多附件推理 |

其中 4 份代表性复杂作业又进行了逐题、逐文件的独立复核，给出允许合理裁量的分数区间，而不是用一个主观单点分数强行判断模型对错。

### 3.2 统一测试条件

- 所有模型接收同一份作业正文、评分标准、图片顺序和结构化 JSON 输出要求。
- DOCX 使用项目现有提取逻辑统一抽取文本和图片；图片通过同一条 OpenAI-compatible `image_url` 消息链发送。
- 不在提示词中提供模型厂商名、历史得分或学生身份。
- 网页截图作业原始评分规则为空，因此统一补充一份显式、可复现的规则，避免不同模型自行猜测量表。
- 对 12 份视觉样本建立字段级人工金标准；不把姓名、学号作为识别目标。
- 选择 4 份差异较大的锚点作业，每个模型各运行 3 次，检验同一输入下的评分波动。
- 每次调用记录输入/输出 Token、总延迟、解析状态、错误事件和按公开价格估算的费用；失败结果可断点续跑。

### 3.3 调用规模

每个模型 40 次有效调用，6 个模型合计 240 次：包括 20 次主评分、12 次字段识别以及锚点的追加重复评分。正式运行中 `glm-4.6v` 出现 1 次连接错误，内部重试仍失败；随后按同一参数只补跑该失败键并成功，最终 240 个目标调用均获得有效结果。报告同时保留“观察到 1 次错误、恢复 1 次”的事实，没有用补跑掩盖可靠性事件。

## 6. 独立审计揭示的评分差异

### 6.1 S013：TCP 客户端/服务器代码

实际代码可以建立一次连接并收发一次消息，但题目要求循环收发，程序完成一次后即关闭。合理区间为 50–70。

- 千问 3.7：50；千问 3.6：60；豆包 Pro：60；豆包 Turbo：60，均在区间。
- GLM Flash：70，在上边界。
- GLM-4.6V：20，对一个可运行但功能不完整的实现处罚过重。

### 6.2 S017：38 题长卷

客观部分为 29/30，但分片计算把每段有效载荷按 1500 而非 1496 计算，综合题也存在实质错误。合理区间为 78–88。

- 千问 3.7：84；豆包 Pro：81，符合证据。
- 千问 3.6：98；GLM-4.6V：99；GLM Flash：100；豆包 Turbo：96，普遍对长文本中的计算和综合题错误扣分不足。

### 6.3 S019：多图网络实验

按题面两个组号应计算出 `S=57`，学生使用了 `18`；另有错误复选项，截图显示 100% 丢包且 NAT 抓包证据为空。合理区间为 45–65。

- GLM-4.6V：53；豆包 Pro：52；豆包 Turbo：57，在区间。
- 千问 3.7：74；千问 3.6：78，偏高。
- GLM Flash：52 虽落在区间，但其解释没有识别关键的 S 值错误，因此属于“结果碰巧合理、证据链不完整”。

### 6.4 S020：多图网络实验

客观部分总体较强，但第 9–11 题正文为空，附件与日志中的 S 值分别出现 35/44，角色 A/B 也冲突。合理区间为 60–80。

- 千问 3.7：75；千问 3.6：78；豆包 Pro：66；豆包 Turbo：62，均在区间。
- GLM-4.6V：100；GLM Flash：96，几乎忽略空答和跨文件冲突。

这 4 份样本解释了为什么 GLM 的历史 MAE 很好、独立复核却较弱：它更容易顺着表面完成度或历史评分尺度给高分；豆包 Pro 的证据判断最稳，但代价很高；千问 3.7 在三者之间取得了最好的可替换性。

## 7. 各模型适用边界

### 千问 3.7 Plus

本轮综合推荐第一。视觉识别 100%，独立审计 3/4，重复评分波动可控；主评分成本仅为豆包 Pro 的约 10.6%。弱点是长卷仍需 2 分钟左右，多图实验也可能漏掉跨文件变量冲突，因此必须配合确定性校验器，而不是直接把模型分数落库。

### 千问 3.6 Flash

速度最佳，P50 仅 2.5 秒，适合页面识别、OCR 后结构化、简单规则作业和深度模型前的证据压缩。深度主观题独立复核只命中 2/4，不宜单独负责复杂作业最终分数。

### 豆包 Seed 2.1 Pro

独立复核 4/4、稳定性最好，说明现有选型不是“质量差”，而是“全量使用的性价比差”。本次主评分平均 0.2253 元，复杂长卷/多图的 P50 在 4 分钟以上。建议从默认模型降为高风险仲裁模型。

### 豆包 Seed 2.1 Turbo

速度和稳定性不错，独立复核 3/4，但对教师已落分网页作业普遍偏低，对多图实验也有明显低估。其平均费用反而高于千问 3.7 Plus，本项目没有足够理由把它作为新默认。

### GLM-4.6V

历史 MAE 最低且价格低，但同一份多图作业重复得到 53/76/83，另一个锚点得到 30/50/50；独立复核仅 1/4。适合低成本第二意见、对照实验或证据抽取，不适合作为自动最终评分的唯一模型。

### GLM-4.6V-Flash

免费、基础识别接近满分，适合非实时影子评测和低优先级批处理。但复杂评分稳定性差，长卷很慢，并出现未识别关键矛盾却给出合理分数的情况，不能因为“免费”直接进入自动落分主链路。

## 8. 推荐的系统改造

### 8.1 从“按厂商调用”改为“按能力路由”

当前多模态分支把平台限制为火山方舟，评分执行也按模型名称选择，并为豆包 Responses 输入单独组装请求。建议增加统一的能力描述，而不是继续堆 `if provider == ...`：

```text
ModelCapability
  supports_images
  supports_native_pdf
  supports_json_schema
  supports_thinking
  max_context_tokens
  latency_class
  pricing_version
```

调用层统一接收 `text_parts + image_parts + response_schema`；具体适配器只负责鉴权、请求格式和用量归一化。路由器按任务选择 `fast_vision`、`deep_grading` 或 `adjudication`，以后换模型时不再修改业务评分逻辑。

相关现有入口包括：

- `ai_assistant.py` 中的多模态平台过滤、评分模型选择、系统评分提示词以及豆包 Responses 输入组装。
- `classroom_app/services/ai_grading_service.py` 中的作业读取和评分服务链。

### 8.2 先确定性判分，再让模型做真正需要推理的部分

本次 38 题长卷存在大量单选、多选、数值与公式题，复杂网络实验也有可以程序计算的 S 值。应把以下工作从 LLM 中移出：

- 单选、复选、精确文本、数值容差和公式题由本地规则直接判分。
- 变量题由服务端根据班级/组号计算标准答案并写入评分上下文。
- LLM 只评分解释、设计、代码质量和图像证据，将子项得分交给服务端求和。

这样可以同时降低随机性、Token、幻觉和不同厂商评分尺度差异。

### 8.3 建立一次抽取、多次复用的证据层

建议先用千问 Flash 做低成本证据抽取，并按附件哈希缓存：

```text
原始附件
  -> 文本/图片标准化
  -> 轻量模型提取客观事实
  -> EvidenceBundle（字段、页码/图片号、置信度、附件哈希）
  -> 千问 3.7 深度评分
  -> 确定性校验器
  -> 必要时豆包 Pro 仲裁 / 教师复核
```

只把不确定图片和结构化证据送入深度模型，可以避免每个模型反复读取完整 DOCX 和 11 张图片，预计还可进一步减少费用与延迟。

### 8.4 增加评分后校验器

模型返回结果后必须检查：

- 各题得分之和是否等于总分，是否超过题目上限。
- 必答题为空时是否仍获得满分。
- 扣分是否引用了真实存在的附件/图片证据。
- 组号、计算变量、设备角色、IP 和日志是否跨文件一致。
- 模型结论与确定性答案是否冲突。
- 深度模型与校验器/第二模型分差是否超过 10 分。

出现上述问题时状态应为“需要教师复核”，不应自动覆盖教师分数。

### 8.5 完善用量、价格和审计日志

生产环境应按作业记录：提供商、模型版本、提示词版本、附件哈希、输入/输出/推理/缓存 Token、重试次数、延迟、价格版本、估算费用和最终是否被教师接受。密钥只从环境变量读取，日志和错误消息不得包含请求头或明文 Key。

本次本地评测已实现上述核心记录格式，但不建议把原始学生作业或完整模型输出提交到 Git；它们保留在被忽略的 `.codex-temp/model-benchmark/` 下。

## 9. 建议上线顺序与验收门槛

1. **第一阶段：影子模式**。抽取至少 100 份新作业，同时运行现有豆包与新路由，只展示差异，不自动落分。
2. **第二阶段：教师确认**。千问方案生成建议分，教师一键接受/修改；记录按题修改幅度和原因。
3. **第三阶段：低风险自动化**。仅对客观题和高置信度识别自动落分，复杂主观题继续人工确认。
4. **第四阶段：动态兜底**。根据真实接受率调整豆包 Pro 仲裁比例，而不是固定全量调用。

建议准入指标：

- JSON/结构化输出成功率 ≥ 99.5%。
- 基础视觉字段准确率 ≥ 99%。
- 独立审计合理区间命中率 ≥ 75%。
- 提供商最终失败率 < 1%。
- 相对当前全量豆包 Pro 的实际费用下降 ≥ 80%。
- 分差超过 10、证据冲突或必答题为空时，自动落分率必须为 0。
- 上线首月持续抽查；任何模型版本或提示词变化都重新跑固定回归集。

## 10. 局限与正确解读

- 本次使用 20 份真实作业，覆盖面比厂商 Demo 更接近项目，但仍不是所有课程、语言和附件格式的统计代表；上线前应扩展到至少 100 份影子样本。
- 8 份人工模式历史分数能用于衡量教师尺度贴合度，但不能代替独立盲评。
- 独立复核目前只有 4 份高复杂样本，适合发现严重失真，尚不足以给出窄置信区间。
- Token 由各厂商接口返回，不同厂商对图片和推理 Token 的计量方式并不完全相同；成本比较以实际计费口径和公开价估算，最终应以账单核验。
- 延迟受服务端负载、网络和深度思考长度影响；本报告适合做当前工程选型，不能被视作模型永久排名。
- 部分原始截图因课程要求本身带有身份字段；评测元数据和报告没有发送或记录学生姓名/学号作为标签，但调用第三方 API 仍应遵守学校的数据授权与保存政策。
