# 智慧课堂服务器写回点名：接口调查与落地路线

> 后续进展（2026-11-09）：服务器开始/结束点名已在授权历史课次真实验证，并清理临时记录；原 16 轮、816 条状态保持不变。下文保留前次调查时的边界；本次产品接入与发布状态以 `smart-classroom-auto-sync-closure-2026-11-09.md` 为准。

调查日期：2026-11-09。第一阶段范围为现有实现、学校官方指南、公开网页构建产物。用户随后授权指定历史课测试，第二阶段完成本机学校小程序已交付代码解析，以及真实服务器单人改签、完整回读、恢复和临时轮次清理。未修改产品代码、部署或开启生产自动写入能力。

## 1. 结论与当前边界

应实现“LanShare 后台以任课教师身份写入学校考勤业务后台，再从学校后台读回核对”。小程序展示学校后台的记录；是否需要重新进入页面、多久刷新，需要实际验收。这里的目标不是发送一条微信通知，也不要求服务器长期运行微信窗口。

现有服务端账号登录及点名读取基础可以复用。**第二阶段已打通真实服务器逐人改签和回读：一名学生 UNCHECKED → CHECKED → UNCHECKED，两次均返回 HTTP 200 / `{"state":"ok"}`，小程序与网页接口完整名单一致。测试轮次已清理，原有 16 轮、816 个学生状态保持不变。** 开始、结束调用已在客户端定位，本次由官方 UI 创建和结束临时轮次，不能据此声称服务器自动开始、结束已验证。产品中的自动写入开关仍关闭。

建议分两段接入：先完成“教师已在官方端发起点名 → 服务器改签 → 双端回读确认”，再完成“服务器选课次 → 开始 → 结束 → 改签”。前一段本身就能覆盖微信手动点名后同步修正的业务，并减少首次接入的变数。

## 2. 本次直接取得的证据

### 2.0 第二阶段新增：真正的小程序业务接口

经学校图标和配置共同定位的本机学校小程序为 `wx30f9e2f391fa6338`，缓存版本 `14`。只读解析已下载的客户端代码，没有执行其中代码，也没有读取微信聊天、密码存储或会话存储。解包后的代码保存在既有受 ACL 限制的调查目录，不进入 Git。

`config/env.js` 的实际 API 基址为 **`https://edu-api.gxufl.com/api`（连字符）**，与网页现用的 `edu_api.gxufl.com`（下划线）不同。`config/request.js` 定义 POST 表单、原始 `Authorization` token 和 `Tenant-Id: 1`。

真实单人改签协议：

```text
POST /teaching/teacherSchedule/changeStuStatus
Content-Type: application/x-www-form-urlencoded
Authorization: <教师登录原 token>
Tenant-Id: 1

checkinCourseId=<点名轮次 ID>
username=<学生学号>
status=<学校状态枚举>
```

当前课堂页、历史轮次名单页和学生历史记录页均使用该调用。`username` 明确来自学生 `no`，不是教师账号，也不是学生数据库行 ID。静态实现未见该调用额外签名；不据此推断服务器必然接受写入。

对应回读为 `POST /teaching/teacherSchedule/viewCheckinCoursesRecords`，表单 `checkinCourseId`，响应为学生数组；必须搭配 `POST /teaching/teacherSchedule/view`（`id/week/dayOfWeek/section`）验证实际课次及 `checkinCourse.id/isStop`。教师课程历史列表为 `viewCheckinCoursesCount({teacherScheduleId})`。

服务器只读实测：使用现有网页登录 token 在连字符域名调用 scoped view 得到 HTTP 200；正确匹配授权课次（2026-2027 第 1 学期、第 2 周、星期日、第 8—9 节、课程代码 E030054B1），实际名单 51 人，`isCanCheckin=true`，当前尚无点名轮次。原有其他课次 16 轮、816 个学生状态已重新保存。全程保留正常 TLS 验证，无新增抓包证书。**只读 token 通用不等于写权限已验证。**

随后在这个已授权课次通过官方 UI 创建并结束临时轮次；服务器仅选一个 UNCHECKED 学生改为 CHECKED，2026-11-09 13:56:55 +08:00 确认，13:56:56 +08:00 恢复确认。验证采用三个视图交叉核对：scoped view 的 `stuList`、小程序历史轮次名单、PC `checkinRecord`。除选定学生外其余 50 人状态未变化。正式历史逐轮保护检查随后通过。

仅在确认临时轮次的完整原状态已恢复后，调用客户端明确使用的 `delCheckinCourseRecord({checkinCourseId})` 清理本次新建轮次，回读确认目标课次再次无点名、原 16 轮及 816 状态均与测试前一致。没有借用或删除其他周记录。清理接口仅为本次授权测试收尾所用，不意味着产品应提供自动删除学校历史考勤的功能。

### 2.0.1 实测确认的登录互斥约束

测试后重新进入官方小程序，原会话跳回登录页。为区分自然超时与主动失效，进行了两次受控服务器登录和三次只读 scoped view：旧 token 在第二次登录前为 HTTP 200；第二次登录生成不同 token 后，旧 token 立即变为 HTTP 401，新 token 为 HTTP 200。未改写考勤。

因此必须把“新登录使旧 token 失效”纳入后续同步实现。现有 `open_authenticated_smart_classroom_client` 每次调用都会登录，不能直接用于高频同步或逐人改签循环，否则会使教师小程序会话失效。

- 同一账号的整次任务复用一个受保护会话，按账号串行；读取和写入不能各自反复登录。
- 后台遇到 401 应保留进度并进入需要教师重新授权状态，不能无限自动登录，与小程序相互挤出。
- 教师显式发起任务时需要说明账号会话互斥；要做到双方长期无感共存，需要学校支持独立集成凭据、多会话能力或正式授权的会话共享方式。仅在本地缓存 token 不能解决教师随后在小程序登录造成的失效。
- 本次已完成所要求的单人接口验证；在处理上述会话策略前，生产自动写入能力继续关闭。

### 2.1 学校明确采用同一套账号

[学校官方使用指南](https://gxufl.edu.cn/upload/833d3c34486846498551c7da284cea1a.pdf)第 2 页说明，PC 与小程序登录账号、密码相同；第 3—4 页说明教师选周次、星期和课节后发起点名，且可以修改历史学生出勤状态。学校课表每天同步教务排课信息。

这支持复用管理中心已有的智慧课堂账号密文配置。第二阶段已核实当前网页登录 token 可用于小程序单人改签；这不等于其他写操作或未来版本均适用。无需普通教师提供学校小程序 AppSecret、微信密码或全局开发者密钥。

### 2.3 状态枚举与显示计数并不完全一致

官方名单组件声明八种状态：`CHECKED`、`UNCHECKED`、`SICK_LEAVE`、`PERSONAL_LEAVE`、`LATE_OR_EARLY`、`STUDY_TOUR`、`PRACTICE`、`VOLUNTEER`，但顶部只展示五组常用计数。因此最终确认必须逐学号比较完整名单，不能只看“出勤人数相等”。本地迟到、早退均需映射到学校合并状态，并保留本地原细分。

## 3. 本项目已有基础与必须补齐之处

源码：`smart_classroom_integration_service.py`、`smart_classroom_attendance_adapter.py`、`smart_classroom_write_service.py`（均在 `classroom_app/services/`）。

已有账号加密配置、来源选择、轮次绑定、预览指纹、逐人差异、账号租约、凭据代次、审计、持久任务与不确定结果回读机制。无需另外建设一套登录系统或按学生启动独立进程。

但当前能力明确为 `start=false/end=false/update_student=false`；worker 类型是 `smart_attendance_readback`。这些是绑定、交接、核对的基础，**不是已经实现的远端写入器**。至少还须补齐：

1. 将本文已验证的单人改签协议接入持久任务；开始、结束须独立核实运行结果，不能一起开放能力。
2. 远端完整轮次生命周期读取。现 `fetch_source_detail` 校验后只返回学生及计数，未保留 `checkinCourse` 的生命周期信息；当前确认范围刻意标记为 `student_status_readback_only`。
3. 创建后的远端 ID 绑定，以及创建成功但响应丢失时找回轮次的方法。目前绑定要求传入已有 `remote_checkin_id`。
4. 区分学生业务身份、点名学生记录 ID、实际排课行 ID、课程列表代表性来源 ID。特别是合班课，不能用同名课程或拼接 ID 替代真实对应关系。
5. 精确、有限的写任务发送与恢复机制；网络调用期间不占数据库长事务，不在页面请求内等待整班逐人提交。

## 4. 推荐的完整执行链

### A. 第一阶段：既有轮次改签

1. 教师启用学校同步并选择该课次的远端已有轮次；校验学年、学期、课程、教学班集合、周、星期、节次及教师身份，不能只按“当前周”猜选。
2. 本地点名结束后，冻结本地结论版本，读取远端完整名单作为基线。按学号匹配；缺号、重复号、名单不一致单独显示，禁止误写其他学生。
3. 生成差异预览。未启用的课次、作废记录、采集失败和待确认状态不生成缺课写入。学校已有病假、事假、研学、实践、志愿等状态默认保留；明确的教师更正另行呈现冲突。
4. 后台按账号串行、有界速率发送已核实的单人改签请求。仅写差异，逐人记录计划版本、旧值、目标值、请求结果和确认结果；不能把本地幂等键当成远端必然支持幂等。
5. 完成后读取完整名单逐人核对，再核对远端轮次已经结束。展示“已核对、失败、待处理冲突、结果未知”各自人数；部分失败不报整班成功。
6. 小程序重新打开该轮次验证展示结果；核验学校后台和小程序读取的是同一轮记录。

### B. 第二阶段：自动创建与结束

补齐周课表、实际排课行身份及定位要求后，在 A 前增加：查找是否存在目标轮次 → 创建/绑定 → 确认轮次已开启 → 按核实的官方协议结束 → 确认已结束。已有轮次默认复用或请教师选定，不自动再开一轮。

“当前周”只用于默认定位。真正提交使用本地课次绑定的教学日期及学校返回的排课标识；支持调课、历史课和学期切换。`curCycle` 的现有前端用法只能证明当前学年学期，不能替代周课表。

学校指南要求教师位置。服务器没有手机 GPS：须核实写协议是否需要位置、精度、采集时刻及是否允许课堂信息预配置。如确需实时位置，应从教师明确授权的设备取得真实定位，或者使用学校正式提供的集成模式；不得把服务器 IP 推算位置或任意经纬度伪装为现场定位。

### C. 中断与双向修订

建议任务阶段：`准备 → 创建待确认 → 已开启 → 结束待确认 → 已结束 → 改签中 → 回读确认 → 完成/部分完成`，另有需重新授权、冲突、结果未知等状态。每阶段持久化，重启后先读回再续行。

- 写请求超时、连接中断、5xx：结果可能已落地，先回读。创建结果无法唯一确定时停止自动重发，避免重复点名。
- 401：停止当前账号发送，核实登录失效规则后有限重新认证；对于已经发出的操作，先核对结果再决定是否重试，避免刷新风暴。
- 409：只有核实学校实际错误语义后才能分类处理，不能套用本平台的 409 含义。冲突重拉后重算，不能盲目循环提交。
- 教师同时在学校端改签：比较“上次基线、最新学校值、本次本地目标”；发生冲突保留学校新决定并请求教师处理，不让轮询覆盖。
- 本地申诉处理改变出勤：形成新的可审计同步版本，按教师设置执行/确认；不悄悄回写。已开始发送的旧版本不得与新版本交错覆盖。
- 暂停同步不抹除已发生的写入。作废本地点名不自动删除学校历史记录；学校端更正需要明确业务操作。

默认每账号一个执行通道，所有账号共享有界 worker 池；学校端限速按实际契约调整。200 人只有状态差异需要提交；不能产生 200 个进程、登录或无限重试。本次无需另做长期压测。

## 5. 剩余自动化接入的最小路线

逐人改签的真实契约已经验证。后续自动开始、结束及账号共存，可请学校技术支持确认正式集成契约，至少覆盖：

| 项目 | 必须确认的信息 |
| --- | --- |
| 登录与授权 | 单人改签已确认 token 通用，新登录使旧 token 失效；还需明确有效期、独立集成授权或多会话方案 |
| 定位课次 | 周课表接口、星期编码、组合节次、合班实际 ID 与名单范围、历史课可操作规则 |
| 开始 | URL/方法/编码/必填字段、真实位置要求、返回轮次 ID、重复创建规则、结果丢失后的查找方式 |
| 结束 | 是否有显式接口或仅依赖结束时间、状态字段、停止学生签到的实际时刻、是否重复调用安全 |
| 改签 | 本文单人路径、表单及 CHECKED/UNCHECKED 往返已验证；其他枚举来自真实客户端，不声称已逐个写入；批量及部分失败契约未验证 |
| 回读 | 完整名单、轮次生命周期字段、读后可见延迟、分页、限流及错误码 |

如果无法提供文档，可在**官方支持的客户端调试/网络诊断方式**下，导出一次指定历史测试课的开始、结束和单人改签请求及响应。正式发布版微信小程序不一定开放开发者调试；不能假定普通教师可直接打开 DevTools，也不能把网页的“点名列表”当成具备三项写操作的替代界面。若需要开发者权限，交由学校运维开启受控诊断。资料分享前去掉密码、token、Cookie 以及无关学生信息，保留字段结构与脱敏关联标识。

本文单人改签已按“备份 → 官方 UI 建立并结束临时轮次 → 服务器改单人 → 双读取链路确认 → 恢复 → 清理 → 核对原历史”完成一次真实验证，无需反复再做。后续开始、结束及会话策略只补相应缺口。失败场景的队列恢复使用隔离合成环境，无须对学校端制造故障或进行压力测试。

若学校既不提供写接口也不支持诊断，可靠保底方案仍是教师在官方端操作、平台生成差异清单并读回确认。需要持续维护桌面微信的 UI 自动化不能等同于无人值守服务器接口方案，应作为独立备用方案评估。
