# 学生单独改签与智慧课堂推送（待审查）

本次改动只保留在本地工作区，未提交、未推送 Git、未部署。线上仍使用此前版本。以下流程和验收均使用隔离合成数据；没有为验收更改真实学生考勤。

## 教师操作

1. 从自动点名中的学生小卡打开“学生签到详情”，选择出勤、缺课、病假、事假、迟到或早退，填写改签理由。
2. 点击“保存”，只保存本地决定、审计与关联申诉处理结果。既有整班自动推送授权同时停止，避免把这次本地改签顺带发送到学校。
3. 点击“保存并推送”，先保存本地，再由后台只更正这一个学生。按钮只有在课程和课次仍有效对齐、学校已开始过本次点名、账号及学生身份可用时才启用；学校已经结束点名仍可更正。
4. 卡片显示本地保存与学校确认的独立结果。学校连接失败不会撤销本地保存；可重试原推送，重试不会再次写入本地决定。

学校状态核对在后台进行，保留输入、焦点和未保存草稿。核对期间仍能保存本地。界面在保存后自动重新核对可推送条件，不要求老师关闭并重开学生卡片。已关闭本地自动采集的课程仍可明确更正有效轮次；已作废或被替代的轮次不能推送。

## 边界与关联行为

- 单人推送不调用学校开始点名或结束点名接口，不创建学校学生，不发送其他同学的状态。原有整班同步与单人更正分别保留授权范围。
- 学校名单仍为准：本地独有学生可保存本地，但不能推送。重复、缺失学号、名单超出已对齐范围或课次变更会停止学校写入。学校研学、实践、志愿或未知特殊状态继续受保护。
- 迟到和早退在学校均映射为其提供的 `LATE_OR_EARLY`；本地保留教师选择的迟到或早退，不因回读而合并。回读同时更新既有学校考勤统计投影，不覆盖本地决定。
- 本地保存、不可变更正收据及后台任务在同一事务内提交。记录版本冲突不保存，界面保留草稿；重复请求使用同一幂等标识，只产生一次本地更正。
- 任务封存教师、学生学号、学校点名 ID、课程课次绑定版本、凭据代次和本地手工决定版本。写入前再次核对，不能因重新对齐而把旧任务转向另一课次。
- 学校请求发出前先记录“结果待核实”。响应丢失或读回失败时只继续回读原点名，不盲目重发。若教师此后又只保存了本地新状态，旧请求继续显示其原目标及回读进度，不冒充新状态已推送。
- 学校明确以 401 拒绝请求后复用自动登录恢复，再有限重试；缺少账号、需要验证码或学校持续不可用会显示原因。本地记录保留。
- 结果未知时，同一学校账号重新验证密码后可以继续只读回查，原授权代次和目标保持封存。更换为另一学校账号不能代查；尚未发送的旧授权也不能因更新密码而自动恢复写入。旧高级核对面板仅处理自己的人工核对任务，不接管单人更正。
- 单人更正进行中或结果未知时阻止重新对齐和新的整班授权。未知结果阻止合班、删除；尚未发送的更正在归档时停止，原始作用域及审计保留。
- 学校预检缓存与并发请求合并有界；网络请求不占用数据库事务。学校投影失败不改变已确认的推送结果，也不触发重新发送。

## 代码入口

- `static/js/login_attendance_student_correction.js`：学生卡片的保存、推送、草稿、门禁、恢复与状态轮询。
- `classroom_app/services/smart_classroom_student_push_service.py`：单人更正收据、学校预检、精确写入及回读。
- `classroom_app/routers/smart_classroom_write.py`：在现有教师课堂点名路由下新增学生更正、状态、预检和原任务重试入口，保留同源与归属校验。
- `classroom_app/db/schema_smart_classroom_auto_sync.py`：新增 `smart_attendance_student_corrections` 表和查询索引，复用既有启动迁移、操作账本和任务调度。没有删除或重建原业务表。
- 原工作流、对齐、合班与删除服务增加单人任务互斥和历史保留；原批量改签及申诉消费者仍使用原有 `change_records` 合同。
